## 1. 巡视主循环（core/engine.mjs）—— 今天最重的部分

### 1.1 真 bug：不走 `world.act` 的模块做成事也被判"空转"

**线上实证**：2026-11-14 15:09，刚偷到 6 处 **11,820 D**，紧接着引擎判定"这一轮什么也没做"，退避 300 秒。下一处解禁就在几秒后，全靠 `idleWait` 的 20 秒巡检才没漏掉。

**根因**：退避保险的条件是 `sleep < 10 && totalActions === 0`，而 `totalActions` 只统计 `world.act` 提交成功的动作。偷菜、帮忙、擂台、52弟玩具摊、游乐馆、站宠护理**全都有自己的回执，根本不经过 act**。

**改法**：新增 `didWork` 标志，六个模块有产出时置位：

```js
let totalActions = 0   // 本轮真正提交成功的 act 动作数
let didWork = false    // 不走 act 的模块做成事也算「有推进」
...
if (r?.saved > 0) didWork = true          // 站宠
if (ar?.battles > 0) didWork = true       // 擂台
if (r.helped > 0) { memo.helpStall = 0; didWork = true }
if (r.games > 0) { memo.gomokuStall = 0; didWork = true }
if (ar.played > 0) { memo.arcadeStall = 0; didWork = true }
// 两处偷菜同理
```

退避条件加 `&& !didWork`。（`3403d52`）

### 1.4 跨进程单实例锁（`bb74a84`）

**问题**：GUI 的「重启」是先拉起新进程、再由新进程接管端口让旧进程退出。旧进程可能还在 tick 里（擂台 30 场 4 分钟、一次偷菜 30 秒），两边用同一个 rev 发 `world/act`：轻则 409 白跑，重则同一笔卖出/买入执行两次，账本和存档互相覆盖。

**改法**：新增 `core/daemon-lock.mjs`（67 行）：

- tick 开始时写 `logs/daemon.lock`（pid + 时刻），结束时**只删自己的**
- 占用者按 `process.kill(pid, 0)` 判活，崩溃留下的死锁自动回收（`EPERM` 按活着处理）
- `engine.tick()` 拆成"拿锁壳 + `tickBody()`"：拿不到锁就跳过本轮（sleep 5），同一占用者只提示一次
- `yuyugu2.mjs`：`SIGINT`/`SIGTERM` 共用 shutdown，等 `engine.busy` 落下来再退出（最多 15 秒）

**测试 11 条**：pid 判活、空锁/重复拿/被占拒绝/死锁回收/释放只删自己的。被占场景用真子进程，不猜 pid 1 在不在。

### 1.5 规则热更新从未生效（`6b007ef`）

**真 bug**：`checkRulesUpdate` 调 `fetchVersion` 时没传登录 cookie。未登录的 `/pets` 页面不渲染带 `?v=` 的 script 标签 → `fetchVersion` 永远拿到空字符串 → 每 30 分钟的版本检查全部当成"没变化"静默跳过。**站点改规则后，托管会一直用旧公式算到下次重启为止。**

## 2. 偷菜（core/social.mjs + core/steal-schedule.mjs）

今天偷菜是改动最多的模块，+142 行集中在 `social.mjs`。

### 2.1 拒绝回执三分类（`3c2f063`）—— 移植自参考 `recordSnipeReceipt`

**问题**：以前所有偷菜失败都走同一条路径：记一行日志、波次照常推进。

**改法**：

```js
export function classifyStealReject({ status, message, clock, expectedAt, earlyRetry }) {
  // 1. 每日上限：封到 CST 次日 0 点
  if (/上限|新手|今天偷过|已经偷过 TA 家/.test(String(message))) {
    return { kind: 'daily-cap', until: nextCstDayStart(clock) }
  }
  // 2. 409 卡在推算解禁时刻 ±2 秒 = 时钟截断抖动：1 秒后重试一次
  if (status === 409 && expectedAt > 0 && Math.abs(clock - expectedAt) <= 2 && !earlyRetry) {
    return { kind: 'boundary-retry', retryAt: Math.max(clock + 1, expectedAt + 1) }
  }
  // 3. 其余（最常见「TA 家现在没有能偷的」）→ 90 秒冷却
  return { kind: 'cooldown', until: clock + 90 }
}
```

**关于文案匹配的一个取舍**：比参考实现多收「已经偷过 TA 家」这种更常见的表述，但**不收裸「偷过」**——因为「这茬已经被偷过 2 个」这类 `stolen` 计数会被误判成每日封顶，代价是把整座岛封到明天，远大于措辞上的宽容。

`boundary-retry` 期间**不推进波次**（`skipAdvance = true`），否则这一波直接丢了。只重试一次，防止死循环。

### 2.2 过期解禁退避（`6e91e0a`）

**问题**：解禁时刻已过但服务端仍报 `steal:false` 的地块/畜栏，以前直接丢弃，要等下一轮全量巡逻（默认 30 分钟）才会再发现 —— 而刚解禁的头几秒正是最可能偷到的时候。

**改法**（`steal-schedule.mjs`，与参考 `guardOverdue` 同构）：

```js
const guardOverdue = (rawAt, isExact) => {
  if (rawAt > now) return { at: rawAt, exact: isExact }
  sawOverdue = true
  if (rawAt >= now - 2 && prevOverdueCount === 0) return { at: now + 1, exact: isExact }
  const backoff = [5, 20, 60, 300][Math.min(3, prevOverdueCount)]
  return { at: now + backoff, exact: false }
}
```

首次给 `now+1` 的宽限（数据陈旧多半是秒级），连续过期按 20/60/300 退避，不对着死岛空转。

### 2.3 掐点提交前 GET 确认（`941e24e`）

**问题**：解禁时刻是本地推算的（成熟 + 保护期），天气翻转、岛主临时浇水、别人抢先都会让它失准。而一次失败的 `visit` 提交要占掉 2.15 秒的 POST 间隔 —— 在解禁瞬间这就是下一家的窗口。线上 11-12~14 每天 **25~59 次**「TA 家现在没有能偷的」白撞，一半的提交槽位浪费在这里。

**改法**：提交前先 GET 一次（不节流、不花体力）：能偷就按最新 `targets` 提交，不能偷就跳过，留给下一轮调度。

顺带修了一个日志 bug：失败日志的时差改成按 `tickClock()`（此刻）算 —— 以前用 `world.now`（上次 refresh 的时刻）减 `seenAt`，永远显示「目标数据 0 秒前拿到」。

### 2.4 目录中断保护（`bcfedf6`）

**问题**：`refreshWatchList` 以前无论扫到第几页，都把本次结果当成"全服现状"整份替换，并删掉"不在名单里"的岛的全部调度记录。目录要连发 60 页 GET，超时/429/断线很常见 —— 只要断在第 3 页，剩下 57 页的岛（可能有几百座、带着已算好的解禁时刻）就全部被清掉。

**改法**：

```js
  let cursor = null, seen = 0, kept = 0, pages = 0, failed = false
  ...
  catch (e) { log('偷菜：读目录失败：' + e.message); failed = true; break }
  ...
  if (failed) {
    const merged = { ...(memo.stealWatch || {}), ...watch }
    memo.stealWatch = merged
    memo.stealWatchAt = now - every + 300   // 5 分钟后重试
    log(`偷菜：目录中断于第 ${pages + 1} 页（已见 ${seen} 座），沿用旧名单合并，5 分钟后重试`)
    return merged
  }
```

只有完整走完目录才整份替换 + 清理。中断时**调度记录一律不动**（立刻重扫等于每轮巡视都卡在超时上）。

```js
if (res.status === 401) { stats.errors++; throw Object.assign(new AuthError(), { status: 401 }) }
if (res.status === 409) throw Object.assign(new ConflictError(json.error || '状态冲突（rev 已变）', json), { status: 409 })
if (res.status === 429) { ... throw Object.assign(new RateLimitError('站点限流（429）', retry), { status: 429 }) }
```

**为什么是 bug**：409/429/401 的分类错误以前没挂 `status`，调用方所有 `e.status` 分支（擂台 429 特判、偷菜回执状态机、日志里的 HTTP 码）**从来没命中过**。

### 6.2 掐点改用服务端时钟区间校准（`178c8b0`，`http.mjs` +54）

不再用单一 `serverNow` 点估计，改为区间校准，掐点按区间边界取保守值。

### 6.3 重试边界（`bbe0735`）

收紧到"服务端去重的写接口"；演练模式在 HTTP 层兜底拦截（不再依赖上层每个调用点自觉）。
