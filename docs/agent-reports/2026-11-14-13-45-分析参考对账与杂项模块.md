## 0. 结论摘要

1. **reconcile.mjs 不是金币/库存/经验/税务的账本对账，而是“交易是否执行”的因果对账。** 它核对的是 operation UUID、rev、prestate 字段、visit 计数器和岛日配额；金币/库存只是用 freshWorld 重新锚定，经验和税务完全不核对。
2. **我们的 ledger 有自校验，但只到“日志 vs state.json vs 服务端补账”这一层，没有会计恒等式校验，也没有告警。** 而且发现一处确定的漏记：偷菜罚款 `fine` 从 `social.mjs` 返回后，`engine.mjs` 从未记入支出。
3. **52弟没有遗漏的每日额度或兑换。** 当前规则只有 4 个游戏，`NPC.daily=52`、`GOMOKU_PAID=10`，我们都覆盖了；参考实现也没有兑换逻辑。
4. **update-notifier 监测的是参考项目自己的 GitHub package.json 版本，不是站点规则 hash。** 我们的规则热更新已经比它更贴近站点，但缺少“同版本内容变化检测、规则状态持久化/GUI、变更告警、派生缓存失效”。
5. **pet-and-battle 的护理/换装/加点/开箱/档案同步我们都有，且数值比参考新。** 参考的 tier 宝箱和幻彩已从线上下线（本次实测），不应实现。
6. **调度的真正差距不是 Worker/PlanCache，而是“双 deadline + 每个后台步骤可被掐点抢占”。** 我们目前只在后台模块开始前检查一次 snipeWindow，模块内部的 8.5 秒等待和 6 秒五子棋求解不可中断。

## 1. reconcile.mjs 对账逻辑

### 1.1 它到底核对哪些量

**参考事实：**
- **金币**：只做两件事。
  1. 发送前 prestate 相等性检查：`rev / coins / state.en / prices / state.iq` 任一不等就拒绝提交（`reconcile.mjs:375-393`）。
  2. 结果未知时用 freshWorld 重新锚定资源，而不是自己算金币差额（`reconcile.mjs:342-360`）。
- **库存**：只在 journal 里存 `stateBeforeRef` / `stateAfterRef` 快照 blob（`reconcile.mjs:133、554、674-715`），用于事后审计；没有“期望库存 vs 实际库存”的核对。
- **经验**：完全没有核对。
- **税务**：完全没有核对；只在 `executeTransaction` 开头归档规则源码 `archiveRulesSource(adapter.rulesHash, ...)`（`reconcile.mjs:426`），供事后追查当时用的是哪版规则。
- **真正核对的是交易因果：**
  1. **operation UUID + 回执优先**：拿到明确响应就按回执定案（`reconcile.mjs:144-211`）。
  2. **rev 因果**：没有回执但 rev 前进，不能证明是自己的 operation 造成的，转 unknown 并保留配额（`reconcile.mjs:166-211`）。
  3. **visit 计数器证明**：用 `state.day + state.cnt['st'+targetId] + state.cnt.steal` 判断一次超时 visit 是否真的执行了（`reconcile.mjs:213-339`）。
  4. **岛日配额预算**：`countOccupiedBudget` 把 confirmed 和 submitted/unknown 的 `possibleIsleIndices` 都算作已占用（`reconcile.mjs:462-485`，`audit/journal.mjs:218-297`）。
  5. **跨岛日扩展**：unknown 的 `possibleIsleIndices` 从发送岛日一直扩到当前岛日，宁可保守占预算（`reconcile.mjs:70-106`）。

### 1.2 它何时发现“对不上”

- 提交前：journal 里 rev 已前进 → `stale-prestate-aborted`（`reconcile.mjs:487-526`）。
- 发送前：live world 的 rev/coins/en/prices/iq 与规划时不一致 → 取消（`reconcile.mjs:528-552`）。
- 发送后：网络错误 / 5xx / 回执丢失 → 标 `unknown`（`reconcile.mjs:622-661`）。
- 下一次进锁：`recoverPendingTransactions` + `reconcileUnknownWithFreshWorld` 收尾（`reconcile.mjs:70-120、432-441`）。
- visit 超时后 25 秒静默窗内无法证明：继续占用配额，并预留 6–15 点体力（`reconcile.mjs:279-282`）。
- 它不会因为“今天账本金额不等于金币变化”而报警；它的输出是交易状态和可用预算，不是财务报表。

### 1.3 我们已有的替代机制

- 【我们已有】日志重放 + state.json 对照，日志为准（`core/engine.mjs:255-267`）；税务从日志重建（`engine.mjs:272-278`）；服务端赚钱榜/税务流水补账（`engine.mjs:306-338`）。
- 【我们已有】409 用响应快照重新规划（`engine.mjs:534-543`）；串门后 `revDirty`（`core/world.mjs:16-19、173-175`）；世界动作带 operation UUID，HTTP 层只对可幂等 POST 重试（`core/http.mjs:103-152`）。
- 【我们已有】GUI 显示“其他变动 = 现金变化 − (收入−支出)”（`gui/popup.js:201-222`）。
- 【我们没有】unknown 交易台账、possibleIsleIndices、visit 计数器证明、跨岛日保守预算。
- 【不值得做】完整 journal 状态机 + 跨岛日预算扩展。我们是单进程、POST 串行、账本不参与并发决策，收益远小于复杂度；我们的 409 重规划和幂等重试已经覆盖主要场景。
- 【不值得做】经验核对：经验不影响现金和决策，服务端是权威值。
- 【值得做】税务告警：现有 `recoverBookFromServer` 只在服务端税大于本地时写日志（`engine.mjs:324-327`），可以加“连续两轮仍不一致”的 warn/GUI 提示，但优先级低。

### 1.4 可落地的对账告警（按优先级）

**P0：偷菜罚款 `fine` 没入账（确定的 bug）**
- `core/social.mjs` 的 `stealFromTargets` 已经统计并返回 `fine`（`social.mjs:1182-1185、1287-1293、1418、1477`）。
- 但 `core/engine.mjs` 三个调用点只记了 `r.value`，从未读 `r.fine`：`engine.mjs:570-572`（掐点）、`609-611`（此刻可偷）、`764-766`（全量偷菜）。
- 后果：金币实际减少了，账本支出没有增加；罚款单次上限 5,000、日上限约 20,000，GUI 的“其他变动”能显示但不会告警。参考实现正是把 visit 的失败赔款作为交易结果的一部分对账的（`reconcile.mjs:213-339`）。
- 建议：三处都加 `if (r.fine &gt; 0) { totalSpend += r.fine; this.credit(0, r.fine) }`。

**P1：现金口径与库存口径分离，再做恒等式校验**
- 现状：`credit(..., { cash: false })` 把偷到的库存按市价记入收入（`engine.mjs:176-202、570-572`），所以 `收入 − 支出` 本来就不等于现金变化。直接拿它和 `dCoins` 比会产生大量误报。
- 建议：ledger 增加 `cashEarn / cashSpend`，`credit` 按 `cash` 参数分别累加；每轮收尾用 `expected = startCoins + cashEarn − cashSpend` 与 `w.coins` 比较（`engine.mjs:792-800` 已有实际值）。差额按已知项目分类：余额税、罚款、手动操作、未知；只有未知残差连续两轮超阈值才 warn/推送。
- 这样 GUI 的“其他变动”也能从“展示差额”升级为“可解释的告警”。

**P1：unknown visit 的轻量对账（参考最值得借的一小段）**
- 我们的 visit 在 `social.mjs:1395-1402` 出错后只打日志，不判断服务端是否已经执行。网络超时可能已经偷到东西/已经赔款，但账本和战报档案都当失败。
- 建议：发送前记录 `state.day / cnt['st'+id] / cnt.steal` 和体力；遇到网络错误或 5xx 后刷新 own world，25 秒内计数器变化 → 视为成功，更新账本和战报；不变 → 视为拒绝，可安全重试；无法判断 → 保留体力/配额保守值。对应参考 `reconcile.mjs:213-339`，不需要整套 journal。
- 这一条价值中等、实现难度中等，但比“完整移植 journal”性价比高得多。

**P2：库存审计**
- 每轮 tick 前后保存 `state.inv` 快照，用动作回执里的 `got` 和已知消耗做归因；对无法解释的增减按物品每天只报一次。参考本身也没有做这件事，属于增量能力，不是补参考的缺。

## 2. npc-toy-stall.mjs（52弟玩具摊）

  - 盲盒：`{ a:'npc', g:'box', k:'start' }` → `{ a:'npc', g:'box', i }` × 3

  - `GOMOKU_PAID = 10`（带难度 `d` 的计奖五子棋，非平局才计）
  - 五子棋 15×15，难度 1/2/3 倍率 0.8/1.2/1.5
  - 只有四个游戏，**没有商店、兑换或其它每日额度**。

### 2.2 我们已有的

- 【我们已有】五子棋额度判断：`paidLeft = GOMOKU_PAID − cnt.gomokuPaid`、`dailyLeft = NPC.daily − cnt.npc`、`maxGames = min(...)`（`core/npc.mjs:11-20`）。

- 【我们已有】卡牌/猜拳整批提交，批大小受 `R.WORLD.maxActions` 限制（`npc.mjs:166-181`）；盲盒 start → 3 次 pick（`npc.mjs:148-165`）。
- 【我们已有】额度满时零 HTTP 返回并只打印一次原因（`npc.mjs:21-33`）。
- 【我们已有】`nextWake` 有午夜 0 点全额度刷新事件（`core/planner.mjs:2056-2063`），额度没打完时 60 秒唤醒（`planner.mjs:2138-2148`）。

### 2.3 我们缺少的 / 值得做的

- 【我们没有】**中断后继续打服务端已开局的 `state.npcG`**。参考在 slice 里先检查 `state.npcG`：gomoku 直接解题提交 `end`，box 继续 `pick`（`npc-toy-stall.mjs:491-503`）。我们进程重启、或未来加抢占后中途退出，下一次会重新 `start`，服务端 `npcG` 被覆盖；已解出的局面白费。
  - 【值得做，低优先级】在 `playGomoku`/`playOther` 开头识别并续打 `state.npcG`。注意如果玩家正在浏览器里手动玩，续打会干扰他；可以加“开局时间在 5 分钟内且本地没有主动放弃记录”的保护。
- 【我们没有】**每个后台步骤前可抢占**。参考的 slice 在加锁前、发送前都查 `shouldAbortFn`（`npc-toy-stall.mjs:429-431、533-535`），一次调用最多一个 `POST`。我们的 `playGomoku` 一次跑 10 局，每局 2 个 POST，最长约 40–60 秒，中途无法让路给偷菜解禁。
  - 【值得做，高优先级】不是照搬“一次一 POST”，而是在每局开始前、每次 `world.act` 前调用 `shouldYield()`；被抢占就返回部分进度，下一轮继续。具体见第 5 节。
- 【我们没有】**精确的 NPC 唤醒时刻**。参考 `computeNextNpcWakeSec`：有未完成局或额度未满 → `now + 2`；额度满 → 次日自然日边界 + 5 秒（`npc-toy-stall.mjs:360-380`）。我们额度没打完时固定 60 秒。
  - 【不值得做】单独为 NPC 改成 2 秒：我们把当天额度放在一次 tick 里连续打完，60 秒只影响“被抢占/失败后”的恢复；如果加了 yield，则可以让模块返回一个 `nextWakeHint`（如 2 秒），随下一次 `nextWake` 取 min，这比无条件 2 秒安全。
- 【我们没有】参考的 `remainingNonVisitUnknown` 阻塞和锁内 reconcile（`npc-toy-stall.mjs:462-468`）。
  - 【不值得做】我们单进程无并发交易台账，409 重规划已覆盖；完整引入会带来不必要的复杂度。
- 【不值得做】参考的“一次调用一个 POST”本身。我们的卡牌整批 40 条、五子棋每局 2 个 POST，请求数已经很低；真正的问题是长循环不可抢占，不是批量。
- 【可选】参考的五子棋求解器用 4 个开局 + beam/VCF 兜底（`npc-toy-stall.mjs:316`），我们的是贪心 + 抖动多路线（`core/gomoku.mjs:175-196`）。如果实测胜率低于 90%，提升求解器比调度优化收益更高；这属于算法优化，不是行为差异。

## 3. update-notifier.mjs（版本通知）

### 3.1 它监测什么、触发什么

- 监测**参考项目自己的 GitHub 仓库** `package.json` 的 `version`，不是站点规则 hash（`update-notifier.mjs:4-8、33-45、52-64`）。
- semver 比较（`update-notifier.mjs:10-29`）；GitHub contents API 失败后回退 raw.githubusercontent（`52-74`）；超时 4.5 秒（`8`）。
- 默认每 2 小时检查、banner 每 2 小时重复（`6-7、110-127、330-339`）。
- 触发：日志 banner（`77-95、304-309`）；可选飞书 webhook，按 `lastWebhookNotifiedVersion` 去重（`238-263`）；状态持久化到文件（`184-201`）；`inlineTag()` 把版本提示拼进 daemon 日志行（`345-347`）。
- `checkNow` 会重新读磁盘上的 package.json，识别“已经 git pull 但进程还没重启”（`265-321`）。
- 它不会自动更新、不会重启进程、不会清理缓存。

### 3.2 我们已有的规则热更新

- 【我们已有】从 `/pets` 页面抓 `pets.js?v=` / `app.js?v=`（`core/rules.mjs:18-35`）；下载 `pet-world-rules.js?v=` 并缓存（`127-168`）；每 30 分钟检查一次（`engine.mjs:415-422`）；版本变化时热替换并补喂 `clockStart`（`rules.mjs:193-210`）；游乐馆规则独立热更新（`rules.mjs:12-15、56-96`）；失败回退缓存（`rules.mjs:116-124`）。
- 这比参考的“只看自己版本并提示”更贴近站点；参考的模式不适用于我们的规则文件。

### 3.3 缺少的环节 / 值得做

- 【我们没有】**同版本内容变化检测**。
  - `checkRulesUpdate` 发现 `v === currentVer` 就直接返回 null（`rules.mjs:195-197`），而 `loadRules` 的“缓存超过 1 小时重拉”只在启动或版本变化时被调用（`rules.mjs:127-168`）。站点如果改了 `pet-world-rules.js` 内容但不换版本号，运行中进程永远用旧内容。
  - 【值得做】每小时抓一次规则文本并算 SHA-256，与加载时记录的 hash 比较；变化则写入缓存、重新 import、补喂 `clockStart`，并告警。成本约 100KB/小时。
- 【我们没有】**规则状态持久化/GUI**。`rulesVersion` 在 `engine.mjs:7` 被 import 但从未使用；statusSnapshot 没有规则版本、加载时间、上次检查错误。参考会把 update status 持久化并在 GUI/日志展示（`update-notifier.mjs:184-201、265-321`）。
  - 【值得做】在 memo/state.json 里存 `rulesStatus`：`version、source(cache/live)、loadedAt、checkedAt、changedAt、consecutiveFailures、lastError`；`statusSnapshot` 和 GUI 概览展示；连续失败 3 次以上 warn。
- 【我们没有】**规则变更的显式告警/可选 webhook**。现在只有一行 info 日志（`engine.mjs:420`），异常被完全吞掉（`engine.mjs:422`、`rules.mjs:207-209`），规则检查连续失败在日志里看不出来。
  - 【值得做】变更和连续失败都写 warn，可选飞书/其它 webhook；按版本号去重，避免每 30 分钟重复。可以参考 `update-notifier.mjs:238-263` 的去重方式，但不需要它的 semver/GitHub 机制。
- 【我们没有】**规则变更后的派生状态失效**。热替换后我们每轮都会重新 `planRound`，但 `memo.stealSchedule`（按旧生长/保护期算出的解禁时刻）、`memo.stealScanAt` 等是跨轮持久化的。
  - 【值得做】规则 `changed` 时标记 `stealScheduleStale`，下一轮强制重新扫目录/重算；`externalSoldRatio` 是经验学习值，不必清。参考不涉及站点规则，所以这条是我们自己的改进。
- 【我们没有】**结构校验**。现在只检查 `applyActions` 是否存在（`rules.mjs:159-163`）。规则里缺少 `b12ConfigureClock`、`gomokuReplay`、`cropStage` 等我们实际依赖的导出时，可能到运行中才报错。
  - 【值得做】加载时列出依赖导出做一次性检查，失败回退上一个可用缓存并告警。
- 【值得做，低优先级】**缓存文件选择按 mtime 而不是版本可靠性**。`cachedRulesFile()` 取缓存目录里 mtime 最新的一份（`rules.mjs:38-44`）。如果旧版本文件被触碰（同步工具、杀毒、手工复制），离线启动可能加载旧规则。当前缓存里就同时存在 11×11、无 `GOMOKU_PAID` 的 `rules-4be1c2b4.mjs` 和正常的 `rules-05a5c445.mjs`；一旦误加载旧版，`GOMOKU_PAID` 为 undefined，`playGomoku` 的 `maxGames` 变成 NaN，会静默地 0 局。建议用“最近成功版本指针”（如 `cache/rules-current.json`）而不是 mtime 选文件。
- 【不值得做】GitHub 自身版本通知、semver 比较、2 小时 banner、飞书升级提醒这一整套。我们是本地部署、用户自己控制拉取；真正要盯的是站点规则变化，不是自己仓库版本。

## 5. live-daemon.mjs / controller.mjs 主循环调度

### 5.1 参考的机制

- **优先级三段式**：Phase A 狙击快车道（`live-daemon.mjs:37、118-120`）→ Phase B 经济控制器（`122-144`）→ Phase C 后台维护（`381-566`）。
- **双 deadline / 硬抢占**：controller 求解用 `maxTickSolveMs=45s`，并在 `T_unlock − prepLead − 14s` 前 `worker.terminate()`（`live-daemon.mjs:38-39、123-143`；`controller.mjs:398-409、541-552`）。
- **每个后台 slice 前重查** `shouldBlockBackgroundWork`，并把 `shouldAbortFn` 传进 slice（`live-daemon.mjs:394、411、430-438、457、472、488-490、522-531`）。
- **控制器锁内流程**：`withAccountLock → fetchWorld → reconcileUnknown → envelope → solve → compile → execute`（`controller.mjs:57-59`）；未知交易预算预留 `applyUnknownReservations`（`102-108`）；异步模式锁内重取 world、rev 非农事兼容、cache invalidate（`424-627`）。
- **诊断降级**：`consecutivePlanInvalid` / deferred 计数，连续无效时关闭 stability 检查（`live-daemon.mjs:149-154、265-276`）。
- **空闲预热**：只在 farmWake 45 秒内预热 PlanCache（`604-663`）。
- **其他**：sleep clamp 250ms–120s、500ms 切片（`887-920`）、错误 sleep 10 秒（`969`）、SIGTERM/SIGINT（`825-826`）、pid 文件（`870-873`）、日志行带 GET/POST 统计和更新 tag（`964-966`）。

### 5.2 我们已有的 / 更好的

- 【我们已有】tick 内顺序执行 + `busy` 防撞 + 失败指数退避 30–600 秒（`engine.mjs:983-1011`）。
- 【我们已有】`idleWait` 自适应只读巡检，间隔 20–300 秒，`watchOnce` 六类提前唤醒（成熟、动物、蟹笼、被偷、偷菜解禁、D 币突变 10 万），见 `engine.mjs:1023-1151`。这比参考的固定 sleep + 预热更省请求，也更适合我们的单账号。
- 【我们已有】偷菜体力预留、`physicalPrepLeadSec`、`snipeWindowOpen` 在后台模块前让路（`engine.mjs:472-499、627-640`）。
- 【我们已有】`nextWake` 的事件候选比参考多：作物成熟、动物、体力下一滴、换岛日、0 点、长夜、鱼时段、额度驱动、偷菜解禁、idle cap（`planner.mjs:2000-2280`）。
- 【我们已有】GUI 重启交棒带 revive 兜底和端口独占（`server.mjs:205-273`），比参考只写 pid 文件更强。
- 【我们已有】POST 串行化、服务端时钟区间校准、幂等重试边界（`http.mjs:31-69、103-152`）；参考的 controller 锁内规划我们不需要。

### 5.3 我们缺少的 / 值得做的

**P0：把 snipe 检查和“可让路”前移，并贯穿后台模块**
- 现状：主规划/提交先跑（`engine.mjs:501-554`），然后才检查 `shouldSnipe`（`556-584`）；之后 `snipeWindow` 只计算一次（`627-640`），传给各模块作为“是否启动”的门闩，但模块内部不再复查。
- 后果：
  - tick 开始时如果解禁窗口已临近，前 8 轮经济提交（每轮 2.15 秒）可能先把窗口拖过去；`watchOnce` 能提前唤醒，但不能中断正在跑的 tick。
  - 五子棋一局求解最长 6 秒 + 2 个 POST；擂台一场 8.5 秒 + POST；修仙/游乐馆也有 5–19 秒等待。窗口在模块中途打开时，我们不会停。
- 【值得做】：
  1. tick 开头先算 `shouldSnipe`，命中就直接进偷菜，把主规划放到偷菜之后。
  2. 每轮规划前、每个后台模块的每次 `world.act`/`sleep` 前调用 `shouldYield()`；`sleep` 改成 500ms 分片或可中断的 Promise。
  3. 给 `arenaDaily`、`playGomoku`、`playOther`、`xianRound`、`arcadeRound` 增加 `shouldYield` 参数，被抢占时返回部分进度而不是抛错。
  4. 用现有的 `physicalPrepLeadSec` 作为硬截止：进入“解禁前 prepLead + RTT”后，禁止任何新的后台 POST。对应参考的 `shouldAbortFn`（`live-daemon.mjs:438、488-490、530-531`）和 `shouldBlockBackgroundWork`（`394`）。

**P0：五子棋求解不要阻塞事件循环**
- 我们的 `solveGomoku` 是同步 CPU 循环，单局预算 6 秒（`npc.mjs:53-58`，`gomoku.mjs:175-196`），而 GUI HTTP 服务和引擎在同一进程。求解期间 GUI 状态接口也会卡住，且无法被 snipe 中断。
- 【值得做】把 `solveGomoku` 放 Worker，或至少每 N 条路线 `await setImmediate()` 让出事件循环；这样既能保持 GUI 响应，也能在让出点检查 `shouldYield`。这是借参考“重规划放 Worker”的模式（`live-daemon.mjs:38-39`），不是搬它的 PlanCache。

**P0：重启交棒的跨进程双写窗口**
- 现状：`server.mjs:205-273` 先 spawn 新进程，新进程启动 server 后立即 `engine.run()`；旧进程在 `portUp` 后才 `process.exit(0)`。旧进程如果正在 tick，会在新进程已开始写世界时继续发 POST，可能造成操作丢失、账本重复或 `state.json` 竞争。
- 参考用文件锁保护每笔交易（`reconcile.mjs:20-62`，`isProcessAlive` + gate 串行化回收死 PID）。
- 【值得做】二选一：
  1. 启动时获取一个粗粒度 daemon 锁（`data/daemon.lock`，内容 pid + startedAt；启动时若 pid 存活则等待/拒绝；退出时删除；死 pid 可回收）；
  2. 重启前 `engine.stop()` 并等待 `busy === false`（带 30 秒超时），再 spawn 新进程。
- 第 1 种改动小、也顺带解决 `--no-server` 双开；推荐。

**P1：信号与 pid**
- 【我们没有】SIGTERM 处理；`yuyugu2.mjs:136-140` 只有 SIGINT。参考同时处理 SIGTERM/SIGINT（`live-daemon.mjs:825-826`）。
- 【值得做】加 SIGTERM 与退出清理（`savePersist`、删 pid/lock）。Windows 计划任务/服务管理器停止进程时通常发 SIGTERM 或直接 TerminateProcess，至少能保证优雅退出的路径存在。

**P1：可观测性**
- 【我们没有】把 `client.stats`（GET/POST/错误数，`http.mjs:23`）放进 tick 日志或 GUI。参考日志行带 GET/POST 统计和版本 tag（`live-daemon.mjs:964-966`）。
- 【值得做】在 `describeNext` 或 tick 收尾日志加一行 `GET/POST/429/规则版本/规则检查失败次数`，排查限流和“规则过期”会快很多。

**P2：错误恢复**
- 参考错误 sleep 10 秒，我们指数退避 30–600 秒（`engine.mjs:998-1007`），我们更好，不需要改。
- 参考的 `consecutivePlanInvalid` 降级是针对它 45 秒重求解的；我们的 `planRound` 很轻、409 已经重规划、`stuckCool` 也防自旋。【不值得做】。
- 参考的 PlanCache 空闲预热（`live-daemon.mjs:604-663`）对我们也没有价值：我们的规划是毫秒级，预热收益远小于复杂度。【不值得做】。
- 看门狗：参考也没有真正的 watchdog，只有 pid 文件和主循环；我们的 GUI revive + 端口独占已经更强。【不需要移植】。
