### 2.2 我们明确缺/做错的事项（可落地）

1. **空地种植缺“任意缺口药材”循环**
   - 参考 `REF-X:474-478`：在 jingu/lingcao/linglan 之后，还会遍历 `HERB_ENTRIES_DESC`，只要 `needHerbs[herbId] &gt; 0` 且库存+地里不足就种。这样宗门委托要的赤芝/冰莲/雷竹等也能补种。
   - 我们 `OUR-X:397-399` 直接跳到“最高级药材”。结果是委托/送礼需要的非丹方药材永远只能靠买或等自然库存，委托可能长期交不了。
   - **值得改（中高）**。直接用 `needHerbs` 做循环即可。

2. **`alignLogForDoubleHarvest` 缺 equip/stipend/task/talk**
   - 参考 `REF-X:1155-1193` 的 log 对齐动作顺序：equip → finish → 吃回灵 → 吃培元 → sit/rise → stipend → task → talk → 浇水 → 播种/买种 → 卖 → 预购种 → 学功法 → 打水。
   - 我们 `OUR-X:612-668` 缺 `equip`、`stipend`、`task`、`talk`。当其他动作都不可用时，我们可能推不动 log%4，导致熟地双倍吃不到；同时这些日常也被拖到后面。
   - **值得改（中）**。把 `findNextDailyTalkNpc`（3 次）、`stipend`、`findTurnInableSectTaskIndex` 加进对齐循环；equip 可复用 `pickMainTech`/每日一次判断。

3. **收获排序缺“丹方瓶颈优先”**
   - 参考 `REF-X:1296-1315`：先算 `needHuilingNow/needPeiyuanNow`，把“当前丹方还缺的药材”排在卖价高的普通药材之前。
   - 我们 `OUR-X:685-689` 只按 `HERBS[p.c].sell` 排序。结果可能是卖价高的赤芝先收，回灵丹/培元丹的关键 lingcao/jingu 后收，炼丹晚一截。
   - **值得改（中）**。用 `computeAlchemyHerbTargets` 的 `needHerbs` 给熟地打 `urgentNeed` 权重，排序 `urgentNeed desc → sell desc → idx`。

4. **收获过程中缺“紧急起炉”与体力预留**
   - 参考 `REF-X:1324-1337`：每收一块前先判断 `isUrgentCauldronReady()`；若熟地收获会把灵力压到 `COST.brew=5` 以下，直接停止收获，先保住起炉。
   - 我们 `OUR-X:691-706` 没有这段，可能先把灵力花在收获上，导致当天回灵丹起不了炉。
   - 参考还在浇水/播种前用 `minReservedEnForRipeOrBrew()`（熟地=2，临炉=5）预留（`REF-X:1259-1264,1394-1429`）；我们 `OUR-X:734-756` 只检查 `en &gt;= COST.water/COST.plant`。
   - **值得改（中高）**。加一个 `minReservedEnForRipeOrBrew()` 并在收获、浇水、播种三处使用。

5. **种子预购缺 +2**
   - 参考 `REF-X:1225`：`neededSeeds = empty + upcomingHarvestCount + 2`。
   - 我们 `OUR-X:651-659`：`empty + upcomingHarvestCount`。少 2 颗意味着下一批收获后可能缺种，播种要等买种 POST。
   - **值得改（低）**。直接加 2。

6. **培元丹底仓：s&gt;=8 而不是 s&gt;=9；r=0 + autoFuse 时留 3**
   - 参考 `REF-X:332-351`：
     - `s&gt;=8` 且允许突破时，底仓 `r+1`。
     - `autoFuse &amp;&amp; r==0 &amp;&amp; s&gt;=8 &amp;&amp; shouldAllowBreakPolicy` 时，底仓 `max(3)`，即“1 颗突破 + 2 颗融合”，在进入筑基 1 层的零修为窗口同批融合。
   - 我们 `OUR-X:264-274`：用 `s&gt;=9`，且 `r===0` 时没有 hold=3（只从 r&gt;=1 起保留融合 2 颗）。
   - 影响：在 r=0 s=8 时我们会把培元丹吃掉/卖掉，突破+融合的窗口要等下一轮炼药；而且 s=8 就已经有较高成功率，晚一层才留丹会让突破更晚。
   - **值得改（中）**。把 `&gt;=9` 改 `&gt;=8`，并补 r=0 的 hold=3 分支。

7. **收获后紧急起炉没有覆盖 lv&gt;=5 的突破需求**
   - 参考 `REF-X:1358-1373` 用 `isUrgentCauldronReady()`，其中 `needPeiyuanUrgently = lv&lt;5 || 库存&lt;heldFloor || (可突破 &amp;&amp; s&gt;=8 &amp;&amp; 库存&lt;r+1)`。
   - 我们 `OUR-X:710-715` 只判断 `(sim.lv||1) &lt; 5`，lv&gt;=5 时要等到第 8 步（`en&gt;=85` 或田里没事）才炼培元丹。
   - **值得改（中低）**。把 `isUrgentCauldronReady` 的培元分支补全，收获后就能立刻起炉。

8. **下次唤醒缺“有丹方材料时等灵力 tick”**
   - 参考 `REF-X:1697-1699`：`waitingOnPlotEnergy = !brew &amp;&amp; (有回灵材料 || 有培元材料)`。
   - 我们 `OUR-X:935-948` 只在“有熟地/干地/空地”时把 `waitingOnPlotEnergy` 置真。若田里全在生长且都浇过水、灵力又不足以起炉，我们可能一直睡到灵力 88 或午夜，炼丹被拖几小时。
   - **值得改（中高）**。在 wake 里补 `hasBrewIngredients(sim,'huiling') || hasBrewIngredients(sim,'peiyuan')`。

9. **秘境：只试一个区域、beam 6、不试配招模板**
   - 参考 `REF-X:985-1037,901-979`：`AREAS` 按未通关优先、再按等级降序；每个区域 × 每个候选配招都先 `slots` 再 `rin` 再 beam 搜索；beam 宽 14。
   - 我们 `OUR-X2:171-262`：只选 `areas[0]`，beam 默认 6，且当前配招固定；`slots` 只在批次开头按整体战力换一次。
   - 影响：可能出现“当前区域/配招打不过首领，但换一套配招或降一个区域能过”，我们直接判定进不去，浪费当天 3 次秘境额度。
   - **值得改（高）**。先把 beam 提到 14，再在 `planRealm` 里对每个候选区域用 `chooseLoadout` 的候选集做 2~3 套配招探测；配招切换要作为第一条动作发出。

10. **斗法：体力门槛过低、不试配招、重打策略**
    - 参考 `REF-X:1554-1575`：
      - 普通斗法：`surplus &gt;= 10+16=26` 且 `en &gt;= 45`，且 `en-10 &gt;= minReserved`。
      - 有胜利委托：`surplus &gt;= 10` 或 `en &gt;= 22`。
      - 每个 NPC 用 `hseed(d,npcId,nextDfN,stone,cv.xp)` 确定性预演，并遍历配招模板。
    - 我们 `OUR-X2:489-533`：`fightFloor = realmLeft&gt;0 ? 25 : 10`；首胜只要求 en&gt;=25/10；已胜目标门槛 22/40；不试配招。
    - 影响：灵力 10~25 时就可能开打，把本应留给秘境/收获/起炉的灵力花掉；且当前配招打不过的目标会被跳过，而不会换配招再试。
    - **值得改（高）**。把普通斗法改为 `en&gt;=45 &amp;&amp; surplus&gt;=26`，有胜利委托用 22；再给每个 NPC 试 2~3 套配招。注意我们的重打已胜目标比参考更积极（参考只在有胜利委托时重打），这本身是合理增强，可保留，但要用体力门槛约束。

11. **秘境也是同样的体力门槛问题**
    - 参考 `REF-X:1540-1552`：`(surplus &gt;= 21 || en &gt;= 75) &amp;&amp; en-15 &gt;= minReserved`。
    - 我们 `OUR-X2:396-410`：只要 `en &gt;= 15` 就进。
    - **值得改（高）**。与斗法共用 `minReservedEnForRipeOrBrew` 的口径。

12. **委托刷新时机早于确定性秘境/斗法，且本地任务列表是“假”的**
    - 参考 `REF-X:1577-1583` 把 `tasks` 放在整批最后；`REF-X:1507,1555` 用 `hadTodayTasksInitially` 保证“本批只交/只依赖今天开局时真实存在的委托”。
    - 我们 `OUR-X2:355-377` 在批次最前面 `tasks`，本地 `A.act` 用 `rand=()=&gt;0.99` 模拟出一份服务端不会给的随机任务列表；随后 `winTaskLeft()`（`OUR-X2:497-514`）和 `turnInSectTasks()` 会读这份假列表。`tasksJustRolled` 只挡住了交委托，没挡住“为假胜利委托优先打斗法”。
    - **值得改（中高）**。两个方案任选：
      - 把 `tasks` 移到批次最后（与参考一致）；
      - 或保留在前，但 `winTaskLeft()` 在 `tasksJustRolled` 时返回 false，等下一批真实列表。

13. **事件/章节选择：权重与成本保护差异很大**
    - 参考评分 `REF-X:661-763`：

## 三、combat-engine.mjs 与 core/battle.mjs

结论：`OUR-B` 是 `REF-C` 的近乎 1:1 移植，且是超集：

- 函数清单对比：REF 有的函数我们都有，REF 没有任何我们没有的函数；我们额外有 `noteBattleOutcome`、`getBattleRecord`、`blendBattleRecord`、`loadObservedPanels`、`defaultLockRoot` 等真实战绩/存储增强。
- 战斗公式逐项一致：
  - 20 回合（`REF-C:79,101`）；
  - 闪避 `clamp(0.02,0.40, 0.04+(foeAgi-meAgi)*0.006+被动闪避+0.25)`（`:165`）；

  - 反击 `0.65*(0.85+0.3rng)`（`:211`）；
  - 平局按剩余 HP 比例（`:218-220`）；
  - 效用 胜 1 / 平 0（arena 0.5）/ 负 −0.2（arena 0）（`:246-251`）；

  - 配点断点、零速暴击武器 minSpd 3/4/6、Lv13/Lv14+ 断点、vit 8、str 26→27（`:478-618`）；
  - 候选武器4/护甲3/护符5（`:760-831`）；

  - 守家后验默认 800 局、缓存 512（`:975-1030`）。
- 唯一可落地差异：
  1. **守家模拟局数**：参考默认 800，我们 `OUR-SOCIAL:816` 用 `guardTrials=400`（`OUR-CFG:283` 注释说为了不拖过解禁窗口）。400 的配对标准误更大，可能把“换 1 件装提升 1%”误判成显著或相反。**值得改（低）**：600~800，或对已有点档案的目标用 800、未知面板用 400。

  3. 参考的缓存 key 不含 minGain/z，我们的含（更多 miss，无正确性问题）；不必改。
- 参考没有“按对手面板选技能”的额外启发式：`pickSkill` 就是武器技能优先 + 已激活状态跳过 + 等级/技能集过滤 + 最后技能兜底（`REF-C:49-66`），我们完全一致。所谓“按胜率阈值换装”就是 `minGain/z`，我们已经移植。
- 参考的 `executeTransaction`/journal/预算/committed raid 是经济调度架构，不属于战斗启发式；`executeWithTacticalLoadout` 的换装锁/恢复/预计算决策校验我们已移植。
