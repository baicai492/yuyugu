# 三、`execution/npc-toy-stall.mjs`（574 行，问题 2）

## 3.1 参考实现到底做什么

- **规则常量**：`NPC.daily=52`、`GOMOKU_PAID=10`、15 路、难度 1/2/3 倍率 0.8/1.2/1.5、0.1% 中 100 万 D（`rules/pet-world-rules.js:301-307`）。只有胜利发奖；输/平不扣任何东西；平局不计次数；五子棋计奖局只在前 10 局且非平局时增加 `gomokuPaid`（`795-827`）。
- **求解器**：`npc-toy-stall.mjs:4-310` 是完整五子棋评分、局部候选、贪心+束搜索，并用站点规则 `gomokuAI/gomokuReplay` 做 oracle 逐手复演；`solveGomokuForSeed` 用 4 种开局、贪心后束搜索，最后必须 `gomokuReplay === 'win'`，否则抛错（`316-354`）。
- **每日配额**：`cnt.npc`；达到 52 后，只有“盒子继续开/结束”和“五子棋以 d=1/2/3 开局（练习局）”还能提交（`rules:795-806`）。练习局不领奖、不消耗计奖额度。
- **切片行为**（`391-574`）：
  1. 先零 HTTP 判断：`used&gt;=52` 且没有未完成棋局 → 直接 `quota-complete`，不发请求（`410-426`）。
  2. 手操游乐馆 `state.arc.cur` 存在 → 让位，唤醒 `min(now+5, arc.resumeAt)`（`430-441`、`470-481`）。
  3. 账号锁 + unknown 对账后拉最新世界（`445-467`）。
  4. 有未完成的**计奖**五子棋 → 用存档 `seed/d` 求解并提交一次 `{g:'gomoku',k:'end',mv}`（`488-495`）。
  5. 有未完成的盒子 → 只提交一次 `{g:'box',k:'pick',i}`，选第一个未开格（`496-503`）。
  6. 还有额度且 `paid&lt;10` → 开一局 `{g:'gomoku',k:'start',d:3}`（`516`）。
  7. 否则剩余额度一次性提交 ≤40 个 `{g:'card'}`（`517-519`）。
  8. 每次切片只发一个 POST；确认后唤醒 +2 秒，配额满则到下一个自然日 +5 秒（`528-529`、`561-571`）。
- **接口**：`GET /api/pet/world`，`POST /api/pet/world/act`，body `{rev, operation, actions}`，`actions` 为 `{a:'npc',g,k,...}`。
- **每日上限处理**：完全依赖本地 `cnt.npc` + 规则原文；没有硬编码 52 以外的逻辑。盒子存档字段 `pk/left/me/np` 在规则里真实存在，参考实现读 `npcG.pk` 没有 bug。

## 3.2 我们的对应物

`core/npc.mjs` + `core/gomoku.mjs`：

- `playGomoku`（`core/npc.mjs:11-107`）：读 `cnt.npc`、`cnt.gomokuPaid`，每天最多 10 局；6 秒求解预算；只提交本地验证为胜的棋谱；求解失败则直接开新局（不提交败局）；平局不计次。
- `playOther`（`core/npc.mjs:121-190`）：按配置选择 `card/rps/box`；抽牌/石头剪刀布整批提交；盲盒 `start → 3 次 pick`，从实时回包的 `box.pk/left` 选未开格。
- `core/gomoku.mjs:1-201` 是离线多路线试走求解器，`scripts/selftest.mjs:42-53` 验证三档难度均能赢。
- 我们的默认配置：先五子棋，剩余额度抽牌；`box` 默认关闭（`core/config.mjs:216-233`）。

差异：

- 参考实现剩余额度**只抽牌**，不碰 rps/box；我们可配置三种，默认抽牌，行为更灵活。
- 参考实现对未完成计奖局必须求解成功才发 `end`，失败抛错；我们求解失败改开新局，避免提交败局，但会留下未完成 `npcG`，下一轮继续覆盖。两者都不会额外扣次数，安全。
- 参考实现每次切片只发一个动作；我们的盒子一局连发 4 个请求（start+3 pick），请求更多但当天总额度一致。
- 我们读取实时 `box.pk/left`，参考实现读取存档 `npcG.pk`，两者等价；参考不是 bug。

结论：玩具摊整体 **B（已有等价）**，只需把“剩余额度抽牌”的优先级和“求解失败不提交败局”保持住即可，不需要移植。

# 四、`audit/` 这套东西对我们的价值（问题 3）

## 4.1 `audit/journal.mjs`（365 行）

- 内容寻址 SHA-256 blob、按账号分目录、按规则 hash 归档规则源码（`journal.mjs:6-173`）。
- 追加式 `events.jsonl`；按操作 UUID 做 O(delta) 尾部索引，重建每个事务的最新状态：`planned → reserved → submitted → confirmed/rejected/unknown/aborted`（`221-242`）。
- 保守预算占用：已确认 + 已提交/未知事务都算占用，未知事务按“可能落在哪些岛日”保守计（`243-267`）。
- 已确认卖出按岛索引聚合，反推市场深度（`288-330`）。
- 密钥/ Cookie 强制脱敏（`354`）。

**对我们的价值：有，但只需要一个子集。**  
我们目前只有 `core/logfile.mjs`（日志解析/记账），没有事务日志；`world.act` 虽然带 operation UUID（`core/world.mjs:169`、`core/http.mjs:123`），但进程崩溃/超时后无法知道服务端到底执行没有。最小可移植集合：

1. 每个 POST 记录 `{ts, opId, endpoint, revBefore, revAfter, actions, out, stateDigest}`。
2. 用 operation UUID 做幂等索引，崩溃重启后能对账 unknown。
3. 归档每次运行使用的规则文件 hash（我们已经有版本化文件名，但没存 hash）。
4. 密钥脱敏。

不必照搬完整的内容寻址 blob 和预算占用；我们不是多 worker 共享偷菜预算的架构。

## 4.2 `audit/replay.mjs`（534 行）

- 对 xian 批次用归档规则 `xsAct` 重放，检查 `xs.log/stone/en/lv/xp` 漂移、灵力/金币/库存守恒（`replay.mjs:162-284`）。
- 对一般随机批次做“回执条件化”的守恒检查：金币、体力、库存、每日配额（`394-507`）。
- 输出 `consistent*`、`model-drift`、`illegal-action-in-batch`、`not-identifiable`。

**对我们的价值：有，且比 journal 更直接。**  
我们已经在本地用站点规则模拟 xian 和 arcade；把“提交前状态 + 回执 + 提交后状态”保存下来，就能离线回答“是我们算错了，还是服务端改了规则”。建议先做：

- `replayXianBatch(beforeXs, actions, afterXs)`：用 `core/xian-rules.mjs` 的 `act` 逐条重放，对比关键字段。
- `replayArcade(g, seed, shots)`：已有 `core/arcade.mjs:193-198` 的 `verifyShots`，可直接复用。
- 一般动作只做金币/体力/库存的粗守恒，不值得为每个市场动作建完整影子模型。

## 4.3 `audit/report.mjs`（352 行）

- 输出裁决分类：`mechanical-or-conservation-defect`、`rolling-deferral-defect`、`identifiable-decision-regret`、`estimated-suboptimal-candidate`、`ex-ante-consistent`、`not-identifiable`（`report.mjs:9-225`）。
- 关键点：xian/npc 事务在无重放缺陷时直接判 `ex-ante-consistent`，**并不会评价 xian 策略好坏**（`report.mjs:46-64`）；它主要评价的是统一目标函数下的农场/市场决策后悔值。

**对我们的价值：低。** 我们的规划器是规则/启发式，没有统一目标函数、没有 L/U 弱对偶上界，`identifiableDecisionRegretLowerBound` 无从谈起。即使移植，也只能得到“重放一致/不一致”，这部分 replay 已经覆盖。

## 4.4 `audit/reference-solver.mjs`（1799 行）

- 独立枚举候选批次：等待、全卖、按档卖、按件卖、所有配方 n=1..max、配方对/链、体力+加工、stockBuy+加工/卖、农场/谷仓成熟动作（`reference-solver.mjs:324-700`）。
- 场景树非预期性评估、偷菜准备/结果应用、拉格朗日弱对偶上界；输出 `identifiable`、`exhaustiveCertified`、`nodesVisited`、`actualLegal`、`actualContinuationValue/UpperBound`、`bestAlternative`、`identifiableRegretLowerBound`、`estimatedReferenceDelta`（`708-1322`）。
- 它**不覆盖 xian、npc、arcade**，这几类在 report 里直接短路。

**对我们的价值：不适用。** 它是为“统一滚动视野经济内核”写的独立反事实求解器，和我们的规则式规划器、动作 schema、目标函数都不同。移植成本极高，结论也无法直接指导我们的日常托管。

**audit 总结论：journal + replay 的轻量版值得做（A，子集）；report/reference-solver 不值得（C）。**
