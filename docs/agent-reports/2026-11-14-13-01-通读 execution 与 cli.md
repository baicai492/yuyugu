## 1. `ref/execution/http-client.mjs`（438 行）——建议 A（部分）

**职责**
统一硬化 HTTP 会话：Cookie 规范化、Origin/Referer、分桶限速、幂等性分类、429/5xx/网络错误重试、服务端时钟校准、RTT EWMA。关键数据结构是“路径→最后发送时刻”的限速桶、幂等 POST 白名单、服务端时间区间 `[lo,hi]`。

**具体策略/阈值**
- 幂等 POST 白名单：`/api/pet/world/act`、`/api/pet/battle`、`/api/pet/battle/buy`、`/enhance`、`/respec`、`/train`、`/api/pet/state`；并且必须带非空 `body.operation`（`ref/execution/http-client.mjs:19-27,124-131`）。
- 非幂等 POST（visit/help/chest/equip/points/huancai）在超时、连接中断、网络错误、5xx 时**一次都不重试**（`:8-17,293-294`）；429 例外。
- 分桶限速：GET 50ms；world-act/visit/help 2200ms；battle-equip/battle/state 1200ms；default-write 300ms；跨写最小间隔 120ms；请求超时 15000ms；幂等重试 2 次、限流重试 2 次（`:112-122,139-142`）。
- 退避：网络错误 `350*attempt`（`:346`）；502/503/504 仅幂等重试 `450*attempt`（`:402-407`）；429 优先 `Retry-After`（上限 10000ms），否则 `1500*used`（`:389-400`）。
- 时钟：用响应头 `Date` 与响应体 `now` 的秒级截断构造区间，收敛 offset；漂移容差 `min(250ms, elapsed*0.0005)`；`|offset|&lt;=120ms` 钳 0；`sleepUntilServerSec(target, extraOffsetMs=35)`（`:185-240`）。RTT EWMA `0.7*last+0.3*sample`（`:378-381`）。

**我们的对应物与差异**
`core/http.mjs`：POST 严格串行 + 2.15 秒最小间隔（`core/http.mjs:14,26-35`）；超时 30 秒；所有 POST 统一重试 3 次（`:64-69`）；网络 `500*(attempt+1)`、429 `json.retry*1000+200`、5xx `1000*(attempt+1)`（`:74,87-97`）；409 转 `ConflictError`（`:86`）；RTT EWMA 相同（`:59-60`）。没有幂等白名单、没有分桶、没有服务端时间区间校准，Cookie 只在启动时读一次。

主要风险：
1. `core/http.mjs:64-97` 对 `equip`、`points`、`chest`、`train`、`buy` 等无 operation 的 POST 也会在超时/5xx 后重试，可能重复开箱/重复花钱。
2. 30 秒超时会把整条 POST 队列卡住 30 秒，掐点偷菜期间可能直接错过窗口；参考值是 15 秒。
3. `core/social.mjs:1022,1066-1069,1088-1094` 的等解禁时刻用本地 `Date.now()` 与服务端派生的 `at` 比较，本地时钟偏差会直接导致早发/晚发；参考用校准后的 `sleepUntilServerSec`。

**A 类改法**
- 在 `core/http.mjs` 增 `IDEMPOTENT_POST` 集合与 `isIdempotent(path,body)`：GET 与白名单+operation 才允许 `maxIdempotentRetries=2`；其余 POST 仅 429 重试，网络/5xx 直接抛出。
- 默认超时从 30s 降到 15s；给 `world.act` 等关键写单独可配。
- 增 `observeServerClock({reqStartMs,respEndMs,serverSec,dateHeader})`，维护 `[offsetLo,offsetHi]`，导出 `serverNowSec()` / `sleepUntilServerSec(target,35)`。把 `core/social.mjs` 等解禁等待从 `Date.now()/1000` 改为该函数。
- 分桶可在验证站点真实限制后再加：GET 50ms、battle 系列 1200ms、world-act 保持 2200ms；不确定时至少保留现值 2.15 秒，勿贸然降。

## 2. `ref/execution/reconcile.mjs`（742 行）——建议 A

**职责**
账号级文件锁、崩溃后的预发送恢复、未知事务与新鲜世界对账、单事务状态机执行。核心状态：`planned -&gt; reserved-and-durable -&gt; submitted -&gt; confirmed | rejected | unknown | stale-prestate-aborted`，以及 `unknown-state-reanchored`。

**具体策略/阈值**
- 账号锁：`.kernel.&lt;account&gt;.lock`，`wx` 创建，`.gate` 串行化死 PID 回收；超时 15000ms、重试 20ms（`ref/execution/reconcile.mjs:20-62`）。
- 启动恢复：`reserved-and-durable` → `aborted-before-send`；`submitted/unknown` → `unknown`，并把 `possibleIsleIndices` 从最小岛日扩到当前岛日（`:70-106`）。
- 未知 act/xian/npc：`rev&lt;=revBefore &amp;&amp; now&lt;=serverNow` 维持 unknown；`rev` 没变但服务端时钟前进 → rejected；`rev` 前进 → `unknown-state-reanchored`，不归因（`:143-209`）。
- 未知 visit：同日 `cnt['st'+id]` 增长 → confirmed，`coinDelta&lt;0` 推断 lose（`:218-271`）；不到 25 秒保持 unknown，预留体力 `min(15,max(6,expectedEnergyCost))` 并预留罚款 5000（`:274-284`）；≥25 秒按 rev 是否前进决定 re-anchor 或 rejected（`:288-337`）。
- 执行顺序：先预算检查，再 rev 检查（`:462-485`）；距岛日边界 ≤90 秒时候选岛日包含下一个岛日（`:453-458`）；journal 因果检查（`maxKnownRev&gt;revBefore` 或同 rev 已有 confirmed act/xian/npc → `stale-prestate-aborted`，`:487-526`）；可选的 `worldPrestateMatches`（rev/coins/en/prices/iq JSON，`:375-393,528-552`）；先持久化 reservation，再等 `waitBeforeSendFn`，全部落盘后才发送（`:554-601`）。
- 网络错误/无状态码/≥500 → unknown：先持久化响应，再拉取 after-world；4xx 或 `body.ok===false` 且所有 out 非 ok → rejected（`:622-666`）；成功先把 receipt 和内嵌 world 落盘再回调（`:668-703`）。
- act/xian-act 只被非 visit 的未决事务阻塞（`:438-451`）。

**我们的对应物与差异**
没有 journal、没有事务状态机、没有账号锁。已有的恢复能力：
- 409：`ConflictError` 携带响应体（`core/http.mjs:86`），引擎用 `e.data.state` 重新规划并 `continue`（`core/engine.mjs:537-541`）。
- visit/help 会作废 rev：`core/social.mjs:110-117,735-738` 标 `revDirty`，`core/world.mjs:160-162` 在下次写前强制 refresh。
- 没有“请求已发出但没回执”的处理：网络错误重试耗尽后直接抛给引擎，日志一行后继续下一轮。
- 一个具体漏洞：`core/world.mjs:167-190` 的多批提交里，如果第 2 批抛错，第 1 批已经执行并更新了 `world.state`，但 `all` 的 earn/spend/tax 和 `lastOut` 不会返回给引擎，`core/engine.mjs:532-550` 也不记账；GUI 今日收支会漏掉已成功部分。

**A 类改法**
- 新增 `core/txjournal.mjs`：JSONL 或原子 JSON，记录 `{txid, operation, kind, revBefore, actions, energyReserve, cashReserve, status, sentAt, response}`；状态至少覆盖 `planned/reserved/submitted/confirmed/rejected/unknown`。
- 在 `core/world.mjs` 的每批提交前写 `reserved`，发送后写 `submitted`，收到响应写 `confirmed/rejected`；捕获超时/网络/5xx 且无法判定时写 `unknown` 并抛 `UnknownResultError`。
- 下一轮 `engine.tick` 在规划前先 `reconcileUnknown`：拉最新 world；若 `rev` 前进 → 视为已生效，re-anchor，不重发；若 `rev` 未变且 visit 计数/coins/en 未变 → rejected；仍不确定就保留 unknown 并预留体力/罚款，禁止把它当“没发生”重新规划。
- `world.act` 改为每个 batch 结束就通过回调或异常附件返回 `partial` 汇总，让引擎即时 `credit()`；这样 409/中途失败不再漏账。
- 账号文件锁：单进程部署下可标 C；若允许 GUI/脚本/第二实例共用 cookie，则应移植 `withAccountLock`。

## 13. `ref/cli/shadow-daemon.mjs`（449 行）——建议 C（只读防火墙可 A-）

**职责**
只读影子进程：严格 HTTP 防火墙、邻居合成、dry-run controller、Layer-3 独立审计、JSONL 与 latest-status。

**具体策略/阈值**
- 只读防火墙：仅 `/api/` 且仅 GET，否则抛错；15s 超时（`ref/cli/shadow-daemon.mjs:23-50`）。
- 邻居合成：schedule 中 ready/120s 内目标优先，再 marked+目录，按 spots/level 排序，最多 `maxNeighborProbes=6`，逐个 GET visit（`:156-213`）。
- dry-run controller：sendActFn/sendVisitFn 直接抛防火墙错（`:231-249`）。
- Layer-3 独立审计：允许前缀动作 `sell/craft/wait/stockBuy/eat/coffee`，maxSteps 1、maxSearchNodes 80（`:251-275`）；终端清算净值（`:277-280`）；rev 变化跟踪（`:282-295`）；JSONL + latest-status.json（`:298-345`）；间隔 min 30 默认 180（`:375`）。

**我们的对应物与差异**
我们只有 `cfg.dry` 分支：`core/engine.mjs:398,517-520,564,641,661,692,708,733,747` 等逐处检查，`core/npc.mjs`, `core/arena.mjs`, `core/xian.mjs` 内部也有 dry 分支。没有传输层强制防火墙，也没有独立审计/JSONL。C。

低成本 A-：给 `createClient` 增加 `{ dryRun }`，在 `request()` 入口对非 GET 直接抛出（可放行白名单 GET）；这样即使某个模块漏写 `!cfg.dry` 也不会误写。参考的 Layer-3 审计依赖其统一 solver，移植价值低。

## 14. 横向易漏项清单

**重试/退避/超时/限速**
- 参考：幂等 POST 2 次、限流 2 次、非幂等 0 次；15s 超时；GET 50ms、world-act/visit/help 2200ms、battle 1200ms、跨写 120ms。
- 我们：所有 POST 3 次；30s 超时；全局 2.15s 串行、GET 无间隔。主要风险是非幂等写重复与超时卡队列，不是限速过松。

**409 / rev / 未知结果**
- 409 与 revDirty：已有 B（`core/http.mjs:86`、`core/engine.mjs:537-541`、`core/world.mjs:160-162`、`core/social.mjs:110-117,735-738`）。
- 未知结果：缺失 A。最直接的现实漏洞是 `core/world.mjs:167-190` 多批提交中途抛错时，前几批的成功结果不入账。

**请求顺序与并发**
- 我们 POST 全局串行（`core/http.mjs:26-35`），比参考的分桶更保守；世界写、visit、help、equip、battle 不会并发，正确性安全。
- 需要保持的因果顺序：解禁前补体力/买道具/换装必须在等待窗口内完成，解禁那一刻只发 visit（`core/social.mjs:1080-1143`）；我们已按此排序。
- 擂台 8.5 秒等待不可抢占是唯一明显缺口。

**崩溃/重启恢复**
- 已有：`logs/state.json` 原子写（`core/persist.mjs:34-46`），恢复 stealSchedule/stealState/helpCount/arena 进度/账本（`core/engine.mjs:55-125`）。
- 缺失：事务 journal、发送前 reservation、未知事务恢复；`stealWakeGap`/`stealProbeGap` 等自适应状态未持久化（重启后退回 10/60 秒，不影响正确性）。

**时钟偏差**
- 我们仅用 `world.accept` 的单点 `clockOffset`（`core/world.mjs:101-108`），误差约一个 RTT；`tickClock` 只前进（`:122-127`）。
- 两个具体问题：`social.mjs` 的等解禁用本地时钟；`http.mjs` 不在发送前按服务端时间校准。建议按第 1 节做区间校准，并把 `sleepUntilServerSec` 用在狙击等待。

**对方有而我们完全没有的自动化**
1. 每日宠物护理（feed/clean/rest/play，167 XP/日）——影响战斗养成，优先级最高。
2. 家园宝箱（`/api/pet/battle/home` 的 `chests[].tier`）。
3. 焕彩彩票每日底仓（EV 不确定，先观察）。
4. 程序版本更新提示（部署形态不同，可不做）。
5. 多账号/domestic 约束（当前单账号，C）。
6. 只读影子审计（C，但传输层 dry-run 防火墙值得加）。
7. 统一规划器/PlanCache/worker deadline（架构不同，C；但 arcade 20s、gomoku 6s 的本地求解可考虑 worker 化）。
