## 1. 每日目标全完成奖励：k=4 是什么

### 1.1 规则与奖励

`rules.js` L269-290：

- `GOAL_POOL` 共 17 条，按难度分三档：t=1 简单 6 条、t=2 中等 6 条、t=3 困难 5 条。
- `pickGoals(day, s)` L279-286：按 `[[1,2],[2,1],[3,1]]` 抽 2 简单 + 1 中等 + 1 困难，共 **4 个目标**；排序键是 `worldHash('goal2:' + day + ':' + i)`，所以同一天同一岛况下题目确定；`ok(s)` 会过滤掉不适用题目（例如洒水器全覆盖不出浇水、无动物不出收产物）。
- 因此 **k=0..3 才是四个每日目标；k=4 不是第 5 个目标，而是“四个目标全部领取后的全清奖励”领取动作**。用户问题里的“顺手完成第 4 个目标”更准确说是“顺手把 k=4 全清奖励也领了”。

奖励见 `goalReward` L292-298：

| 领取 | 奖励 | 证据 |
|---|---|---|
| 简单 t=1 | 5,000 D + 一件物品（饲料 10 / 鱼饵 6 / 当季种子 6 / 铜矿 6） | `GOAL_COINS` L278，`goalReward` L297 |
| 中等 t=2 | 15,000 D + 一件物品（当季种子 12 / 鱼饵 15 / 炸药 2 / 铁矿 8） | 同上 |
| 困难 t=3 | 40,000 D + 一件物品（炸药 3 / 红宝石 1 / 当季种子 20）+ `pet:2` | 同上 |
| k=4 全清 | 30,000 D + 祖母绿×1 + 炸药×2 + `pet:3` | `rules.js` L295 |

`pet` 不是站宠经验，而是**擂台装备**：`rules.js` L291 注释明确“困难目标和全部完成还送擂台装备（服务端发）”；我方前端 `E:\lrz\python project\52dmeme\yuyugu\live\pet-isle.js` L762-763 直接渲染为 `＋擂台装备（史诗/稀有）`，`pet:3` 是史诗、`pet:2` 是稀有。也就是说：

- 困难目标单独给稀有擂台装备；
- 四个目标全清再给史诗擂台装备。
- 一天四个目标 + k=4 的基础 D 币合计：2×5,000 + 15,000 + 40,000 + 30,000 = **95,000 D**，另加各目标物品、稀有装备和史诗装备。

### 1.2 规划器如何“顺手”领 k=4

核心函数是 `solve.mjs` L45-65 的 `collectClaimableGoalActions(R, naturalDay, state)`：

```js
const readyOrClaimed = [false, false, false, false]
for (let k = 0; k &lt; 4; k++) {
  if (state.cnt?.['goal' + k]) { readyOrClaimed[k] = true; continue }
  if (goals[k] &amp;&amp; Number(state.cnt?.[goals[k].id] || 0) &gt;= goals[k].n) {
    goalActs.push({ a: 'goal', k })
    readyOrClaimed[k] = true
  }
}
if (readyOrClaimed.every(Boolean) &amp;&amp; !state.cnt?.goal4) goalActs.push({ a: 'goal', k: 4 })
```

它不额外安排任务，只做两件事：
1. 把已经达标但未领取的 `k=0..3` 追加进当前批次；
2. 当四个目标都已领取或在本批内被标记为可领时，追加 `{a:'goal', k:4}`。

规划器有三处调用它，确保“顺手”且同批生效：

| 位置 | 行号 | 作用 |
|---|---|---|
| bucket 预演阶段第 7 步 | `solve.mjs` L3926-3938 | 把 goal 奖励的现金计入后续体力/现金模拟，避免“奖励到账前不敢买/不敢做” |
| 执行阶段 3.5，sell 之前 | `solve.mjs` L6811-6815 | 领掉此前农务/加工等已完成的目标 |
| 执行阶段 4.5，sell 之后 | `solve.mjs` L6826-6830 | 专门处理 `sold 80,000 / 300,000` 这类卖货后才达标的目标，并把 k=4 同批领掉 |

`collectClaimableGoalActions` 一次可以返回 `[k0,k1,k2,k3,k4]`，然后整批交给 `simulateValidBatch` 顺序模拟；由于 k=0..3 已在模拟状态中置位，k=4 的“四个都已领取”校验能通过。测试 17.1 的 Case B/C 就是验证这一点：`tests17.mjs` L141-155 单批 0..4；L157-204 卖货后同批领 sold 目标 + k=4。

## 2. 擂台每日宝箱：gear.daily / 空包 POST / 同锁穿戴

### 2.1 发现的新机制

对方发现每日宝箱状态不在 `/api/pet/battle/home`，而在 **GET `/api/pet/battle/gear` 的 `.daily`**：

```js
daily = {
  trained, chest, chestMax, battles, need, earned, ready, nextAt, ...
}
```

字段含义：
- `chest`：今天已经开过的宝箱数；
- `chestMax`：今天最多能开几个，通常 5；
- `battles`：今天已打的擂台场次；
- `need`：每多少场发一个宝箱，默认 3；
- `earned`：今天已经挣到（可开）的宝箱数；
- `ready`：当前是否有可开宝箱。

测试 17.2 的 mock 明确注释：线上 `/api/pet/battle/home` **没有 `chests` 字段**（`tests17.mjs` L227-238）。旧代码却遍历 `homeData.chests`，并用 `{ tier }` body 去 POST `/api/pet/battle/chest`（`pet-battle.mjs` L330-336）。线上这个分支实际是空转，导致每日宝箱永远不开。

### 2.2 旧 bug 的两个点

1. **找错数据源**：`home.chests` 在线上不存在，应该读 `gear.daily`。
2. **算错“现在能开几个”**：旧逻辑按 `chestMax - chest` 算，0 点时 `chest=0/chestMax=5`，会直接 POST 5 次；但此时 `earned=0`，服务端全部拒绝。`chestMax - chest` 是“今天总共还能开几个”，不是“现在已挣到几个”。
3. **body 格式错了**：线上接口要空对象 `{}`，不是 `{ tier }`。

### 2.3 修法

`pet-battle.mjs` L272-281 新增 `isDailyBattleChestReady(daily)`：

```js
const opened = Number(daily.chest ?? 0)
const max = Number(daily.chestMax ?? 5)
if (opened &gt;= max) return false
if (daily.ready === true) return true
const need = Math.max(1, Number(daily.need ?? 3))
const earned = Number(daily.earned ?? Math.min(max, Math.floor(Number(daily.battles ?? 0) / need)))
return earned &gt; opened
```

随后在 `withGearLock` 内执行 L342-350：

1. `maxDailyChests = max(0, min(10, gearSnap.daily.chestMax ?? 5))`；
2. 只要 `isDailyBattleChestReady(gearSnap.daily)` 就 `postJson('/api/pet/battle/chest', {})`；
3. 用 `cr.body.catalog` 刷新 `gearSnap`（没有就再 GET）；
4. 记录 `got.item.id`；
5. 如果 `daily.chest` 没前进就 break，防止死循环；
6. `recordObservedPanel(st, gearSnap)` 之后再 `planGearAndPoints` + 逐槽 equip。

关键点是**先开箱、后算装备、同锁内完成**：宝箱掉落的传说武器会立刻出现在 `catalog` 里，`planGearAndPoints` 能选中并穿上；如果先算装备再开箱，就会错过这一轮。测试 17.2 第 3 个箱子掉传说武器并断言同锁换上（`tests17.mjs` L272-337）。

另外 `runSingleArenaBout` 增加 `chestMilestoneReached`（`pet-battle.mjs` L546-549）：

```js
const chestMilestoneReached = Boolean(
  boutResp.ok &amp;&amp; usedToday &lt; 15 &amp;&amp;
  Math.floor(usedAfter / 3) &gt; Math.floor(usedToday / 3)
)
```

`live-daemon.mjs` L447-450 在 milestone 时再次 `lastBattlePrepAtSec = 0`，下一 tick 会提前开箱/重穿，而不是等 120 秒的常规 prep 周期。

## 5. 多波次出击时间轴 / 离散口粮连续性

### 5.1 多波次偷菜时间轴

核心在 `snipe.mjs` 的 `recordVisitSnapshot`（L316 起）：

1. `ownerLeft = Number(visitData.left?.owner ?? 999)`（L352），只有 `ownerLeft &gt; 0 &amp;&amp; !owner.newbie` 才继续。
2. 枚举 `allUnlocks` 里所有未来解禁时刻，`maxWavesForOwner = min(3, max(1, floor(ownerLeft)))`（L502）。
3. 每波选取一个 `candT`；下一波必须满足 `candT &gt;= lastWaveUnlockAt + 15`（L517）。这就是“每波之间至少 15 秒”的来源，避免两波准备/请求窗口重叠。
4. 对每个 `candT`，构造一个模拟岛：所有 `unlockAt &lt;= candT` 且未被本 target 已领取的地块/畜栏标记为可偷，然后用 `evaluator.evaluateTargetWave(simBundle, candT)` 评估（L548）。
5. 要求 `profitable &amp;&amp; totalSpots &gt;= minStealSpots &amp;&amp; decisionScore &gt; 0`，才记录 `waveRec`：
   - `waveIndex/unlockAt/exactUnlockKnown/upcomingSpots/projectedScore/projectedEnergyCost`；
   - `plannedPrepActs/plannedBuffActs/plannedStaminaPrepActs/optimalLoadout/numGearChanges/tacticalDecision`。
   见 L555-568。
6. 记录后把本波涉及的 plot/pen 加入 `claimedPlotSet/claimedPenSet`，后续波不再重复计。
7. 入口保存 `upcomingWaves` 和 `waveBundlesByUnlock`（L638-668），供执行阶段使用。

执行阶段：

- 成功后 `_advanceEntryToNextWave(entry, idNum, nowSec, { decOwnerLeft: true, completedUnlockAt })`（L872-878）：
  - `ownerLeft--`；
  - 剩余波只保留 `unlockAt &gt;= max(now+6, completedUnlockAt+10)` 的（L705-706）；
  - 把下一波的 `plannedPrepActs/plannedBuffActs/optimalLoadout/...` 写回 entry（L720-729）；
  - `nextProbeAt = max(now+10, next.unlockAt - 40)`，提前 40 秒准备；
  - 同时更新 `activeRaidSchedule.committedWavesByTargetId`。
- 若 409/边界拒绝，可能 `_advanceEntryToNextWave(..., decOwnerLeft:false)`（L819-825），因为没消耗 owner 配额。
- 输掉时不前进，5 秒 cooldown 后重新评估。
- 没有剩余波时 `nextProbeAt = now + 300`，不再盯这家。

规划器侧：

- `solve.mjs` 接收 `scheduledUpcomingRaids`（L1561）；
- L2052-2071 把已承诺的未来 raid 按 `unlockAtSec` 放进 `scheduledRaidsByU`，并为之前每个 bucket 记入 `futureRaidsAfterU`；
- 执行到对应 bucket 时先执行 raid（L4147+），并用 `buildFutureRaidStaminaSchedule` 给未来波次预留体力，影响当前吃口粮/咖啡/做活的决策。

**相比单波次好在哪：**

- 旧版有 `coalesceUnlockWindowSec`，会把解禁时刻人为合并成一波，导致最早的那批被推迟（`snipe.mjs` L27 注释明确说已移除）。
- 单波次只能吃同一岛主的第一批；而 `left.owner` 允许同一岛主多批（直到配额耗尽）。不保留后续波，第二/第三批要么被完全放弃，要么等下一次扫描/访问，通常已经过了窗口。
- 多波次把每批都按精确解禁时刻排进时间轴，统一在一个 target entry 里推进，避免重复扫描和重复建目标；同时用 `ownerLeft` 上限和 15 秒间隔防止过度调度。
- 对规划器的价值：已承诺的未来波次会进入体力曲线，当前不会把体力花在低价值活上，导致下一波没体力。

**我方现状：没有多波次。**
- `core\social.mjs` L290-312 的 `targetsFromIsle` 完全不看 `info.left.owner`；
- `core\steal-schedule.mjs` 的 `updateIsleSchedule`（L158-280）只选“第一个 EV 达标组”，L245-280 把 `nextGroup` 写进 `rec.upcoming`，后面的组直接丢弃；

- `snipeStaminaReservation`（L518-548）也只按每家最早的 `upcoming` 算一次。

**是否值得加：** 如果我们把偷菜当重要收益来源，值得加一个简化版：
1. 在 `updateIsleSchedule` 里读 `info.left?.owner`，保存 `ownerLeft`；
2. 按 `ownerLeft` 上限（最多 3）继续扫描后续 EV 达标组，间隔 ≥15 秒，存 `rec.waves`；

### 5.2 离散口粮连续性

问题背景：旧版按 `cpe`（每点体力成本）排序，用“前缀贪心”估算补 `d` 点体力的成本。它有两个误差：

1. **小份口粮被大份遮蔽**：比如需要 5 点体力，小麦 +6、番茄 +15；如果番茄每点更便宜，贪心会选番茄，溢出 10 点。溢出本身不总是浪费（可以留给后续活），但在“只需要补一点点”的场景，它会改变成本判断。
2. **未来强制缺口没有定价**：现在吃掉一份盈余口粮，意味着未来某个“必须完成”的农务/加工体力缺口要拿更贵的咖啡或 450 D/点兜底来补；只看当前 CPE 会低估吃掉的真实机会成本。

对方在 v1.4.4 的改法（`solve.mjs`）：

- `buildSameIsleSurplusRationChunks` L5580-5625：
  - 只在同岛还有未来工作且允许 `eat` 时构建；
  - 先扣除未来加工所需原料（`futureCraftNeedByItem`）；
  - 潮汐饭团按每日上限和跨午夜重置计算可用量；
  - 过期零食 `cpe = 0`；
  - 其余口粮 chunk 的 `cpe = edibleOpportunityUnitValue / energyGain`。
- `evalSameIsleCont` L5656-5760：
  - `causalDeficit = max(0, peakFarmCraftDeficitEn - carryEn)`：因果前缀上的峰值缺口；
  - `endDeficit = max(0, totalFutureSameIsleMandatoryEn - netRegenBalance)`：期末缺口；
  - `mandatoryDeficit = max(causalDeficit, endDeficit)`；
  - 用最便宜的 ration chunks 支付 mandatory deficit，然后咖啡（受 `postMidCoffeeCap` 限制），最后 450 D/点兜底；
  - 只有覆盖 mandatory 之后的盈余体力才用于额外工作；
  - 结束时剩余体力按 `nextIsleCarryValuePerEn` 估价。
- 食物选择 L6067-6100：
  - 对 `g = 0..(enMax - curEn)` 做**精确有界离散 DP**，每个物品有 `count`，不是按比例；
  - 注释明确目的：`wheat +6` 这样的细粒度口粮不会被 `tomato +15` 这样的低 CPE 大份口粮遮蔽；
  - 只保留 Pareto 未被支配的 gain 集合；
  - 用 `bestNetImp = deltaWork - cumCost` 绝对净收益替代 `bestRatio`（L5990、L6165-6172），避免比率失真；
  - 会吃掉当前加工原料的候选，只在“乐观上界仍能超过 bestNetImp”时才做精确模拟（L6183-6202）。

**相比旧策略好在哪：**
- 强制未来工作一定被定价，不会出现“现在吃爽了，明天没体力做必须做的活”；
- 细粒度口粮不会被大份口粮遮蔽，补 5 点不需要买 15 点；
- 吃/不吃的判断从“比率”改成“绝对净收益”，不会因为分母很小而放大;
- 盈余口粮和咖啡/自然回复放在同一套机会成本里比较。

**我方现状：部分已有，但完整模型没有。**
- `core\stamina-dp.mjs` 已有工作动作的精确有界背包 + 2D 现金 DP（`allocateStamina` L46-216），和对方 stamina knapsack 同源；
- `core\planner.mjs` L1336-1405 已有 `dp/dpIsle` 两条曲线 + `isleValue` Bellman + `nextIsleValuePerEn`，所以“未来体力价值/带到下一个岛日”这层我们有；
- 但 L1309-1327 的 `costAt` 是**按 CPE 排序的前缀贪心**，不是精确 DP；`energyActions` L117-166 也是贪心；
- 没有 causal prefix deficit、mandatory deficit、ration chunk 定价、跨午夜 snack 重置这些细节。

**是否值得加：**
- 完整移植 `evalSameIsleCont` 不值得：它服务于对方多岛日、多 raid、多分支的 trunk planner；我们的 planner 每轮重算，horizon 短得多，引入这套会让复杂度大幅上升。
- 一个小改**可能**值得：把 `costAt` 从“前缀贪心”换成“对当前 gap 的精确有界 DP”，并保留实际吃口粮的指针顺序；这样能避免大份口粮溢出造成的成本误判。改动局限在 `core\planner.mjs` L1280-1345，风险可控，但收益要先观察是否真的出现口粮浪费/咖啡过度购买。
- 更简单的临时改进：在 `energyActions` 里优先选 `full &lt;= room` 的最便宜口粮，只有当没有能装下的才选最小溢出项；这不是精确 DP，但能覆盖大多数小缺口场景。

**状态标注：**
- 工作体力背包/未来 carry 价值：**【已有】**
- 精确口粮 costAt / mandatory deficit / ration chunks：**【未有】**
- 完整搬运：**【不建议】**
- `costAt` 小改：**【可选，先看症状】**
