## 1. 多波次 raid 时间线

### 1.1 数据来源：当前可偷 vs 未来解禁

`snipe-scheduler.mjs` 的 `recordVisitSnapshot`（316–698）同时解析两类状态：

- **当前可偷**：visit 回执里 `plots[i].steal === true`、`barn[i].steal === true` 的位置，加上 `readyEligible`、`stealableCount`、`projectedScore`。
- **未来解禁**：遍历 plot/pen，凡是 `stage &lt; 3 &amp;&amp; left &gt; 0 &amp;&amp; stolen &lt; perPlotCap`，用 `adapter.exactPlotTimings` / `exactBarnTimings` 算出 `matureAt` 和 `unlockAt`，并叠加 `protectSec` 与守家超时退避 `guardOverdue`（5/20/60/300 秒）。结果汇总成 `futurePlots` / `futurePens`，再合并排序为 `allUnlocks`（484 行）。

注意：它**没有把“现在能偷”和“未来解禁”塞进同一个数组**。当前可偷走 `nowEval`，未来走 `upcomingWaves`；真正的“合并成一条时间线”发生在求解器和执行谓词里。

### 1.2 波次枚举规则（498–593 行）

- 只对 `ownerCanBeStolen` 的目标枚举。
- `candidateTimes` 是所有不同 `unlockAt` 的去重列表。
- `maxWavesForOwner = min(3, max(1, ownerLeft))`：受“今天还能从这个岛主偷几次”限制，最多 3 波。
- 波与波之间至少间隔 **15 秒**：`candT &lt; lastWaveUnlockAt + 15` 直接跳过。
- 每一波累计此前所有已解禁且未被占用的 plot/pen，模拟成 `simBundle`（未来地块标记为 `{stage:3, steal:true, stolen:0}`），调用 `evaluator.evaluateTargetWave(simBundle, candT, { extraUpcomingBundles })`。
- 接受条件：`profitable &amp;&amp; belief.totalSpots &gt;= minStealSpots &amp;&amp; decisionScore &gt; 0`。
- 接受后把该波的地块加入 `claimedPlotSet` / `claimedPenSet`，保证**同一块地不会被算进下一波**；记录 `waveRec` 到 `upcomingWaves`，同时缓存 `waveBundlesByUnlock`。
- 第一波被接受时，如果不是当前 ready，就写成 `upcomingEligible=true`、`expectedUnlockAt`、`exactUnlockKnown`、`upcomingSpots` 等字段。

`ownerLeft` 是服务端按“岛主当日被偷次数”给的剩余额度；`maxWavesForOwner` 和 `ownerLeft` 一起决定波数上限。

### 1.3 立即打还是等：执行层决策

- **立即打**：`hasReadyTargetNow`（1007–1021）检查 `readyEligible &amp;&amp; stealableCount &gt;= minStealSpots &amp;&amp; projectedScore &gt; 0`。为真时 `shouldBlockBackgroundWork`（1027–1036）会让探索、修仙、NPC 等后台工作全部让路。
- **等下一波**：`nextExactUnlockInfo`（948–1005）只挑 `upcomingEligible &amp;&amp; exactUnlockKnown` 的目标，按 `expectedUnlockAt` 最早优先；同一时刻按 `projectedScore` 更高优先；`leadSec &lt; -20` 直接丢弃。
- **已排程约束**：如果 `activeRaidSchedule` 存在：
  - committed 目标按排程里的 `plannedPrepActs` / `numGearChanges` 执行；
  - `evaluatedTargetSet` 里但未 committed 的目标严格跳过；
  - 新发现目标如果 `leadSec &gt; ceil(computePhysicalPrepLeadSec(entry) + 2)`，只设置 `needsRefresh=true`，让控制器重新求解，不贸然打；
  - 如果已经进入物理准备窗口，则走 `unplannedImminentDiscovery` 快速路径。
- **求解器合并**：
  - `collectReadyNeighborBundlesForController`（1140–1175）重新探当前 ready 目标（最多 4 个，20 秒内缓存），按分数排序；
  - `collectUpcomingTargetsForController`（1078–1134）展开每个目标的全部 `upcomingWaves`，wave 0 如果与当前 ready 重复则跳过（1101 行），按 `projectedScore` 取前 10，再按 `unlockAt` 时间排序；
  - 两者一起进入 `buildObservationEnvelope` → `solveUnifiedPlan`，由求解器决定哪些 raid 值得承诺（`committedRaids` / `evaluatedTargetIds` / `truncatedByDeadline`）。

### 1.4 波次之间如何推进和重排

- **胜利**：`recordSnipeReceipt`（765–899）调用 `_advanceEntryToNextWave({ decOwnerLeft:true, completedUnlockAt })`（700–759）：`ownerLeft - 1`，过滤掉 `unlockAt &lt; max(now+6, completedUnlockAt+10)` 的波次，把下一波字段提升为当前波，更新 `nextProbeAt = max(now+10, nextUnlock-40)`，同步更新 `activeRaidSchedule` 的 `committedWavesByTargetId` / `committedRaids`。
- **拒绝/失败**：
  - 解禁时刻之后的普通拒绝会推进下一波，但**不扣 ownerLeft**（服务端没消耗一次偷取机会）；
  - 早 409（发送时刻 ≤ 边界 +250ms）只重试一次 `+1s`；
  - 晚 409（≥ +250ms）不再假重试，直接推进下一波；
  - `win` 之外的 `lose` 会设置 `needsGuardLogSync` 并用战斗快照重评估；`draw` 冷却 4 秒。
- **跨目标重排**：同一个目标的波次是按时间预计算的，不会在执行中重新排序；跨目标重排靠 `recordVisitSnapshot` 的漂移检测（674–694）：
  - committed 目标失去资格、解禁时间偏移 &gt;2 秒、可偷位置变少 → `needsRefresh='committed-target-drifted:&lt;id&gt;'`；
  - 出现新的正 EV 且未被评估的目标 → `needsRefresh='new-positive-ev-target:&lt;id&gt;'`。
- **求解超时保护**：`syncCommittedRaidSchedule`（72–146）在 `rs.truncatedByDeadline &amp;&amp; incomingRaids.length === 0` 时，保留上一个排程里所有 `unlockAtSec &gt; nowRefSec - 2` 的 committed raids，设置 `needsRefresh=true`、`refreshReason='previous-solve-truncated-by-deadline'`。这避免“求解被 deadline 截断，把已经计划好的未来 raid 弄丢”。

### 1.5 判断与移植建议

- **对方架构特有**：整个 `activeRaidSchedule` + `evaluator.evaluateTargetWave` + 统一 EV 求解器 + prep/buff/loadout/stamina 建模是他们的 planner 架构；不建议整体搬。
- **通用的好做法**：每座岛维护“波次列表”；按 `ownerLeft` 封顶；波间隔 ≥ 物理准备时间；累计 claimed 地块避免重复计算；胜利后提升下一波、失败不扣额度；求解截断时保留未来承诺；执行前用最新 visit 快照做漂移检查。
- **对我们是否适用**：**适用，建议移植简化版（P1）**。我们现在的 `steal-schedule.mjs` 每座岛只保留“第一个 EV 合格组”：`updateIsleSchedule`（158–285）按 `groupSpanSec` 分组并只写 `nextAt/nextGroup/nextEV/upcoming`；`stealFromTargets` 每次尝试后直接把 `rec.upcoming=[]`、`nextAt=0`，并设置 `checkAt=now+60`（`social.mjs:1381–1392`）。如果一块地分两批成熟，第二批会在 60 秒后才被重新扫描，容易错过。建议把 `rec` 扩展为 `waves: [{at, plots, pens, ev, exact}]`，最多 2–3 波，成功偷取后调用类似 `advanceIsleWave` 的逻辑，而不是清空；执行前仍然要重新 visit 并重算 EV，不能完全相信静态排程。

## 2. 尾部索引 journal（Tail-indexed ContentAddressedJournal）

### 2.1 它解决什么问题

`ContentAddressedJournal`（`audit/journal.mjs:6`）是 append-only JSONL：

- `appendEvent`（191–200）每条事件一行；
- `writeBlob`（153–164）把 state/request/response/plan 按 sha256 内容寻址存成单独 JSON 文件；
- `stripForbiddenFields`（354–365）写入前去掉 cookie/token/secret 类字段。

旧的 `reconstructTransactions` 每次都会把整个事件文件从头解析一遍，重建 `operation -&gt; 最新状态` 映射。文件到几千行后，planner 每个 tick 都要查 `countOccupiedBudget` / `sumConfirmedSalesByIsleIndex`，读放大严重。

### 2.2 具体机制

新增的核心是 `_syncIndexFromDisk`（105–151）和内存索引：

- `_idxByteOffset`：已经消费到的字节偏移；
- `_idxTxMap`：`operation UUID -&gt; { status, history, possibleIsleIndices, ... }`；
- `_idxStatusCounts`：confirmed / rejected / unknownOrSubmitted 三个桶；
- `_idxSalesByIsle`、`_idxSalesCountedOps`、`_idxPendingSaleOps`：按岛日聚合已确认销售。

每次 `reconstructTransactions`（224–240）只做：

1. `fs.statSync` 看文件大小；
2. 文件变小 → 说明被截断/轮转，`_resetIndex()`；
3. 大小不变 → 直接返回；
4. 变大 → 只 `readSync` 新增字节；
5. 只消费到最后一个 `\n`（132–137 行），尾部不完整行留到下次；
6. 逐行 `JSON.parse` 并 `_applyParsedEventToIndex`（40–103），坏行只增加 `_idxCorruptLines`，不中断。

`_applyParsedEventToIndex` 把同一 operation 的多次事件折叠成最新状态：`planned → reserved-and-durable → submitted → confirmed | rejected | unknown | aborted-before-send`。`possibleIsleIndices` 在非终态时取并集，在 confirmed/rejected 时取精确集合。

`countOccupiedBudget`（247–266）直接查索引：confirmed 和 reserved/submitted/unknown/unknown-state-reanchored 都算占用，rejected/aborted 不算；这是保守配额，避免崩溃恢复期间重复使用当天偷取额度。`sumConfirmedSalesByIsleIndex`（291–316）只增量处理新确认的 act 交易，且 `clockStart` 变化时整体重置。

### 2.3 崩溃恢复到底在哪

**尾部索引本身不是崩溃恢复机制**，它只是读优化。崩溃恢复在 `execution/reconcile.mjs`：

- `withAccountLock`（20–62）：账号级 lockfile，写入 PID；通过 `process.kill(pid, 0)` 判断旧进程是否还活着，死 PID 可安全接管；串行化同一账号的所有临界区。
- `executeTransaction`（400–742）的状态机：
  1. 计算 `worldBefore` 和请求；
  2. 先把 `stateBeforeRef`、`requestRef` 等 blob 写盘；
  3. 追加 `reserved-and-durable` 事件（565–583）；
  4. 执行 `waitBeforeSendFn`（等精确解禁时刻）；
  5. 追加 `submitted` 事件（604–612）；
  6. 真正发网络请求；
  7. 成功 → `confirmed` / `rejected`；网络错误、超时、5xx → `unknown`（622–660）。
- 启动时 `recoverPendingTransactions`（70–106）：
  - `reserved-and-durable` → `aborted-before-send`（请求还没发，安全）；
  - `submitted` / `unknown` → 标为 `unknown`，并把 `possibleIsleIndices` 从已知岛日扩展到当前岛日。
- `reconcileUnknownWithFreshWorld`（120–373）：
  - 有明确回执 → 以回执为准；
  - act 类：rev 没变但时钟前进 → `rejected`；rev 前进且无法归因 → `unknown-state-reanchored`（保守占额度，同时重新锚定世界资源）；
  - visit 类：同一天 `cnt['st'+targetId]` 增加 → 推断 `confirmed`，并用金币差推断 `inferredVisitOutcome`；25 秒静默后计数没变 → `rejected`；跨午夜 → 重新锚定，不误判。

### 2.4 局限

- `appendEvent` 是 `appendFileSync`，**没有 fsync**；“durable”只保证进程崩溃后大概率还在，掉电/系统崩溃可能丢最后几条。
- 索引只在内存里，进程重启后第一次查询仍然从文件头全量 replay；3200 行没问题，几十万行就需要持久化 checkpoint。
- 如果进程死在半行，下一次追加会接在半行后面，整行 JSON 损坏，解析时被计入 corrupt line，这两条记录都会丢。他们的处理是“忽略不完整尾行”，但没有修复半行；这是可改进点。

### 2.5 测试

`phase16-v144-root-cause-fixes.test.mjs` 的 16.1（46–126）：

- 写入 3200 行；
- 冷启动 `reconstructTransactions` + `sumConfirmedSalesByIsleIndex` 正确；
- 热查询 20 次平均 &lt;5ms；
- 外部进程追加 confirmed sale + submitted visit 后，增量索引准确识别 `unknownCount=1`、`countOccupiedBudget('steal')=1`、销售累计正确；
- 新实例冷启动结果一致；
- 文件截断为空后索引重置。

### 2.6 判断与移植建议

- **通用好做法**：append-only 事件日志 + 字节偏移增量索引 + 按 operation 折叠状态 + 坏行容错 + 截断重置。这个模式本身不依赖他们的业务。
- **对方架构特有**：内容寻址 blob、完整的 transaction state machine、按 `possibleIsleIndices` 保守占配额、visit 计数推断，这些和他们的审计/求解器强绑定。
- **对我们是否适用**：**部分适用，建议先移植最小事务日志 + 启动恢复，不要先做 tail index**。我们的 `persist.mjs` 只是原子写 `state.json`（34–45 行，tmp + rename），`logfile.mjs` 是给人看的文本日志，都不能回答“重启前最后一批 world.act 到底发出去没有”。我们的 `http.mjs` 对 POST 默认重试 3 次（64–95 行），如果遇到超时/5xx，理论上可能重复动作（world.act 有 operation UUID 幂等，visit/help 则未必）。最小方案：
  - 在每次 `world.act` / visit / help 前，把 `{operation, path, body, revBefore, status:'submitted', sentAt}` 追加到 `events.jsonl`；
  - 收到回执后追加 `confirmed/rejected/unknown`；
  - 启动时把 `submitted` 但没有回执的记录标为 `unknown`，先拉一次最新 world，再按“rev 是否变化 + 当天计数”决定是否重发；
  - 对非幂等 POST 禁止自动重试，交给恢复流程。
  - 等日志真的到几万行，再加 `_idxByteOffset` 的尾部索引不迟。

## 3. 离散口粮连续性

### 3.1 先澄清“跨轮”的含义

这批改动里的“连续”**不是跨进程持久化的口粮账本**，而是同一个求解器在多个时间桶（bucket）之间的口粮预算连续性：同一个物品不能在一个分支里被吃掉、又在另一个分支里被当成可用库存；未来必须做的农务/加工体力不能现在被钓鱼花掉。真实跨轮的状态仍然以服务端 `state.inv` / `state.cnt` 为准。

### 3.2 精确离散 DP（6067–6160 行）

旧的贪心按“每点体力成本（cpe）”从低到高吃，但遇到离散小颗粒会出错：比如小麦 +6 体力、番茄 +15 体力，小麦更便宜，但贪心可能先处理低 cpe 的大颗粒物品，达到 cap 后把小颗粒标成“已完成”，导致本来可以用小麦精确补齐的缺口被番茄的高成本或溢出浪费掉。

新做法：

1. `G = enMax - curEn`，即本次最多能补的体力；
2. 对每种可食物品，`count` 受库存、每日上限、未来加工预留限制；
3. 有界离散 DP：`dpCost[g]` = 补到 `g` 点体力的最小机会成本，`dpCounts[g]` 记录每种物品用了多少份，`dpFirstIdx[g]` 记录第一份物品类型；
4. 对每个物品的每一份，倒序枚举 `g`；`ng = min(G, g + stepG)`，所以超出上限的部分按“浪费”计费；
5. 得到所有可达 gain 后做 Pareto 剪枝：从大到小扫描，只保留“更大 gain 且成本不更高”的点（6110–6117）；
6. 选择标准从“成本/体力比最优”改为**净收益最大** `bestNetImp = deltaWork - cumCost`，同净收益时取成本更低（6163–6165）；
7. 最终只落地一个“食物类型 + 批次数量”的动作，外层循环在体力变化后可以继续决策。

### 3.3 跨桶连续性：不重复、不漏算

关键函数：

- `buildSameIsleSurplusRationChunks(stWorld, usedExtraMap)`（5580–5630）：
  - 只在该岛未来还有农务/加工时才生成口粮池；
  - `usedExtraMap` 记录前面桶已经吃掉的每种 `id:q` 数量，从库存中扣掉，避免同一份口粮被重复计入；
  - `futureCraftNeedByItem` + `rawPoolAfterCraftReserveGlobal` 预留未来加工需要的原料，**只有 surplus 才允许当口粮**；
  - 每日上限和跨午夜重置都考虑在内（5600–5601）；
  - 按 `cpe` 排序，便宜的先用。
- `evalSameIsleCont`（5656–5766）：
  - `deferredEatReserve` 再次从 chunks 里扣掉“已经承诺给未来桶的口粮”；
  - `peakFarmCraftDeficitEn` 是未来同岛农务+加工需求与自然回复之间的**峰值缺口**；
  - `sameIslePrefixRegenDemand` 保存每个前缀的累计回复和累计农务/加工需求，用于计算因果缺口；
  - `causalDeficit = max(0, peakDefWithDeferred - carryEn)`，`endDeficit = max(0, 未来刚性需求 - 净回复余额)`，`mandatoryDeficit = max(causalDeficit, endDeficit)`；
  - 按 cpe 顺序为刚性缺口买单，不够再用咖啡（午夜后重置/折扣），最后按 `450/点` 罚分；
  - 超出刚性需求的 surplus 才用于未来工作。
- `maxUsefulUEn`（5955）把 `peakFarmCraftDeficitEn` 算进去，避免过度买口粮。
- `farmReserveFloor`（6391–6417）在最终分配时再兜一层未来农务体力下限。

### 3.4 测试

16.4（319–404）：

- en=0，库存小麦（+6，便宜）和番茄（+15，贵），2 块地已熟 → 必须在 b0 先吃小麦再收获，不能等、不能浪费番茄；
- en=6，4 块地 25 秒后成熟，coins=0 → 必须为 25 秒后的收获预留体力，不能现在钓鱼；
- 负控制：en=0、只有昂贵番茄、没有未来农务 → 不能为了低价值钓鱼吃番茄。

### 3.5 判断与移植建议

- **通用的好做法**：有界离散背包 + Pareto 剪枝 + 按净收益选择，而不是 ratio 贪心；这是任何“离散体力/资源补充”都适用的。
- **对方架构特有**：`peakFarmCraftDeficitEn`、`deferredSameIsleFarmEnByEF`、`sameIslePrefixRegenDemand` 这套“多桶因果缺口”模型，只在他们统一 planner 的多时间桶结构里有意义。
- **对我们是否适用**：**只建议移植小 DP 和“未来刚性体力下限”思想（P2）**。
  - 我们的 `planner.mjs` `energyActions`（117–156）是按 `costPerEnergy` 排序的贪心，动态截断 room、扣每日 limit；大多数场景够用，但在“缺口很小、食物颗粒差异大、接近上限”时会选错。
  - 我们的 `planner.mjs` 已有 `keepRipe`（成熟待收+补种）和 `snipeReserve`，取 `max` 而不是相加（1128–1144），这已经是“未来刚性体力预留”的粗粒度版本。
  - 我们的 `stamina-dp.mjs` 是工作分配的 bounded knapsack（46–216），不是口粮选择。
  - 如果线上日志出现“明明有小麦却吃番茄/吃到溢出”的情况，再把 `energyActions` 的贪心换成 `G = need - en` 的小型精确 DP 即可；不需要移植他们整套多桶模型。

## 4. 手动游乐馆保护（state.arc.cur）与 PlanCache 隔离

### 4.1 `state.arc.cur` 是什么

服务端游乐馆状态里：

- `arcStart` 设置 `x.cur = { g, seed, t: ctx.t }`（`cache/arcade-05a5c445.mjs:138`）；
- `arcEnd` 要求 `c = x.cur` 且 `c.g === g`，并且 `ctx.t - c.t &gt;= MIN_PLAY[g]`；
- 成功结算后 `x.cur = null`（145 行）；
- `太快了` 时直接返回，**不清 `x.cur`**（144 行），所以可以重试；
- 玩家按 Esc 中途退出时，前端没有发送 `arcEnd`，`x.cur` 会残留，因此需要 TTL 兜底。

字段含义：`g` 游戏 id（bounce/pool/bowl），`seed` 服务端回放种子，`t` 是 `arcStart` 的服务端处理时刻。

### 4.2 为什么后台一写就会毁掉手动局

站点前端 `/isle-arcade.js` 在 `arcStart` 时捕获了当时的 `world.rev`，最终 `arcEnd` 用这个**旧 rev** 提交；如果期间托管程序发了任何会推进 rev 的写请求，服务端返回 `409 world_conflict`，而前端**不会自动重试**，玩家这一局就丢了。所以让出必须是**全局让写**，不只是“别自动玩游乐馆”。

### 4.3 检测与让出协议

`getManualArcadeStandbyInfo(world, nowSec, options)`（`observations.mjs:302–343`）：

- `ttlSec` 默认 180 秒，最小 10 秒；
- 读 `world.state.arc.cur`；
- `startedAtSec = floor(cur.t)`；
- `resumeAtSec = startedAtSec + ttlSec`；
- `active = now &lt; resumeAtSec`；
- 返回 `{ active, game, startedAtSec, elapsedSec, remainingSec, resumeAtSec, ttlSec }`。

各处让出点：

- `controller.mjs:110–121` 的 `checkArcadeStandby` 返回 `{ status:'standby-manual-arcade', arcadeStandby, nextWakeSec: min(now+5, resumeAtSec) }`；
- 在 pre-solve（449–452）、in-lock 重新取世界后（575–578）、post-reconcile（663）都检查；
- `executeStagedSnipe` 在 fresh world + reconcile 之后检查（1266–1279），返回 standby 和 `nextWakeSec &lt;= now+5`；
- `live-daemon.mjs` 在 staged/controller 返回 standby 时设置 `phase:'arcade-standby'`（101–105、304–314）；
- `isArcadeStandbyNow` 门控修仙（472）、NPC（522）、探索（557）；下次唤醒也 clamp 到手动局结束或 5 秒后（354–368、587–591）；
- `npc-toy-stall.mjs` 在取世界后和 in-lock 后都检查（438–441、476–480），激活时 `nextNpcWakeSec = min(now+5, resumeAtSec)`（560–571）；
- 修仙的 http 代理会在 GET `/api/pet/world` 时更新 `lastInLockWorld`（live-daemon 473–479），保证让出判断用的是最新世界；
- CLI 支持 `--disable-arcade-standby`、`MEME_DISABLE_ARCADE_STANDBY`、`--arcade-standby-ttl`（默认 180，最小 10），日志标签 `arc=yield(game,rem=Ns)`。

测试 Phase 17.5（约 589–780）验证：`state.arc` / `b9Rank` 变化不影响 digest；活跃手动局时 live tick 返回 `arcade-standby` 且**零 POST**；浏览器 `arcEnd` 清掉 `arc.cur` 后下一 tick 恢复并 POST；Phase C 中途 `arcStart` 会中止修仙并跳过 NPC，仍然零 POST。

### 4.4 PlanCache 隔离是什么

`PlanCache`（`execution/async-planner.mjs:92+`，`getValid` 154–235）按 rev、静态农场摘要、约束/目标哈希等缓存求解结果。正常情况 rev 变了缓存就失效；但手动游乐馆、NPC、五子棋、修仙都会推进 rev，如果每次让出/恢复都重算，既慢又浪费。

隔离机制：

- `NON_STATIC_FARM_STATE_KEYS = {'xs','npcG','arc','b9Rank','log','en','enT','enDay'}`（`observations.mjs:160`）；
- `NON_FARM_CNT_KEYS = {'npc','npcWin','gomokuPaid'}`（161）；
- `computeStaticFarmStateDigest`（194–214）只对“农场域”的 state 做摘要，`cnt` 先走 `canonicalizeStateCntForFarmDigest`（176–187）排除非农场计数；
- `isFarmDomainPassiveCompatible`（235–289）：如果 rev 前进，先看 `xs`、NPC 元数据（`npcG` / `cnt.npc` / `cnt.npcWin` / `cnt.gomokuPaid`）、游乐馆元数据（`state.arc` / `state.b9Rank`）是否发生变化；如果这些“隔离域”里有变化，就继续比较农场静态摘要，并用 `advanceTimeOnly` 比较 `en` / `enT`；一致则说明 rev 变化只来自非农场域，缓存可复用。
- `controller.mjs:580–601`：in-lock rev 与 raw rev 不一致时，若 `isFarmDomainPassiveCompatible` 为真，则 `reusedAcrossNonFarmRev=true` 继续用旧计划；否则 `asyncPlanner.cache.invalidate(account)`，返回 `stale-plan-invalidated`，下次唤醒 +1 秒重算。

### 4.5 判断与移植建议

- **通用的好做法**：共享账号/浏览器同玩场景下，检测 `state.arc.cur` 并全局让写，是最直接、最有效的保护；TTL 兜底 Esc；每 ≤5 秒轮询结束状态。任何“人机共用同一账号”的托管都应具备。
- **对方架构特有**：PlanCache 隔离本身；我们目前每个主循环重新规划，没有跨 tick 计划缓存，不需要移植。
- **对我们是否适用**：**非常适用，建议作为 P0 立即移植**。
  - 我们 `core/arcade.mjs` 的 `arcadeRound`（229–315）自己会用 `world.act` 玩三种游戏；`world.act`（`world.mjs:98–132`）每次都使用最新 rev 并 `accept` 新快照。如果玩家同时在浏览器里玩，我们的任意写入都可能让玩家的 `arcEnd` 409，玩家的局就丢了。
  - 我们**没有**手动局检测：`arcadeRound` 只看 `arcLeft`，不会检查 `state.arc.cur` 是否已经被别人占用。
  - 建议做在三处：
    1. 在 `core/arcade.mjs` 增加 `manualArcadeInfo(world, now, ttlSec=180)`，逻辑照 `getManualArcadeStandbyInfo`；
    2. 在 `core/world.mjs` 的 `act` 入口做统一门控：如果 `state.arc.cur` 活跃且不是**我们自己**的本局，抛出/返回 `ManualArcadeStandbyError`；`arcadeRound` 自己调用时传 `ignoreManualArcade:true`，并在 `arcStart` 前先检查是否已有外来手动局，有就整轮跳过；
    3. `helpIsle` / `stealIsle`（`social.mjs:99–107`、`715–719`）走的是 `wpost`，绕过 `world.act`；更彻底的做法是在 `core/http.mjs` 的 POST 层加 `canPost` 钩子统一拦截，白名单只允许我们自己的 `arcStart/arcEnd`。
  - 我们自己开局后，建议在 `arcEnd` 前 GET 一次 world，确认 `state.arc.cur.t/seed` 仍是我们的；如果被玩家接管，直接放弃本局，不发 `arcEnd`，避免互相覆盖。
  - engine 捕获该异常后：记录 `arc=yield(game, rem=Ns)`，保存状态，睡到 `min(now+5, resumeAtSec)`，跳过巡逻、偷菜、擂台、NPC、修仙、探索；`resumeAtSec` 到了或下次世界快照显示 `arc.cur=null` 就恢复。
  - 不要照抄“180 秒 TTL”作为唯一判断：我们自己的局可能超过 180 秒，所以必须用“是否自己持有”来区分；TTL 只用于清理 Esc 残留。

## 5. v1.4.5：`/api/pet/world/act` 带 rev 与 mock 硬化

### 5.1 改了什么

`npc-toy-stall.mjs` 的 `sendFn` 从：

```js
postJson('/api/pet/world/act', { actions, operation })
```

改为：

```js
postJson('/api/pet/world/act', { rev: liveWorld.rev, operation, actions })
```

同时：

- 非 confirmed 时 `nextNpcWakeSec = max(baseNextWakeSec, refWorld.now + 15)`（560–571），避免 NPC 被拒后每个 tick 都重试；
- live-daemon 日志输出 npc 的 rejected/unknown/blocked 状态。

为什么必须带 rev：`/api/pet/world/act` 是乐观并发写接口，服务端用 `payload.rev === world.rev` 判断动作是否基于最新状态；不一致返回 `409 { error:'小岛状态已变化', code:'world_conflict', rev, state }`。NPC 的 52D 动作也是世界动作（消耗资源、改状态），必须遵守同一协议。之前 NPC 是少数绕过统一 `world.act` 包装的裸调用，缺少 rev 后在线上被 409 打回。

### 5.2 “harden mock rev check”防什么

测试里的 mock 以前只校验 actions 结构，不校验 rev，所以“NPC 路径漏传 rev”这种 bug 能通过 CI，线上才炸。硬化后（phase17 测试的 102、421 行附近），mock 在 `Number(body.rev) !== Number(serverWorld.rev)` 时返回和服务端同形的 409，并带 `error/code/rev/state`。这样任何未来的裸调用、忘记 rev 的重构、或用了旧 rev 的路径都会在测试里暴露。

### 5.3 判断与我们的现状

- **通用的协议要求，不是可选项**：任何 `/api/pet/world/act` 调用都必须带当前 rev；任何会改世界状态的非 rev 接口（visit/help 等）之后必须把本地 rev 标脏或重新拉取。
- **mock 硬化是通用的测试好做法**：测试替身必须模拟服务端的关键拒绝条件，否则测试会给出虚假的安全感。
- **我们已合规的部分**：
  - `core/http.mjs:123` 的 `act(rev, actions, operation)` 已经发送 `{rev, operation, actions}`；
  - `core/world.mjs:110` 每次 batch 都传 `this.rev`，并在 `accept` 后更新；
  - visit/help 之后 `social.mjs:106`、`718` 已设置 `world.revDirty=true`，`world.act` 会先 `refresh()`（103 行）；
  - 409 在 `engine.mjs:494–497` 会 `accept(e.data)` 并按最新状态重新规划（但当前批次动作不会重试，见下）。
- **仍值得补的**：
  - 加一个回归测试：mock 的 `/world/act` 在 rev 不匹配时返回 409，并断言所有世界写路径（主循环、NPC、擂台、修仙、偷菜、帮忙）都不会漏 rev；
  - 审一遍 `core/http.mjs` 的 POST 重试策略（64–95 行）：`world.act` 有 operation UUID 幂等，重试安全；visit/help 等非幂等接口不应盲目重试 3 次，建议按路径白名单只对幂等接口重试，其余交给事务日志/恢复流程；
  - 对所有不走 `world.act` 却可能改变 rev 的写接口（擂台、修仙、NPC）明确：要么它们不改 world rev，要么之后设置 `revDirty` 或刷新快照。不能靠“以前没出问题”来假设。

## 6. `observations.mjs` 新增了哪些观察

新增/改动分三类：

1. **手动游乐馆状态**：`state.arc.cur = { g, seed, t }`，通过 `getManualArcadeStandbyInfo`（291–343）解析为 active/剩余时间/恢复时刻。

   - `NON_STATIC_FARM_STATE_KEYS`（160）：`xs`、`npcG`、`arc`、`b9Rank`、`log`、`en`、`enT`、`enDay` 不再进入农场静态摘要；

   - `canonicalizeStateCntForFarmDigest`（176–187）保证只对农场相关计数做规范化。
3. **访客视角的 ownerLeft**：`buildUpcomingVisitBelief` 把 `upcomingTarget.ownerLeft` 透传进 belief（710 行），让评估器知道这个岛主今天还剩多少可被偷次数，从而正确限制波数。

- `arc.cur` 观察和 `ownerLeft` 透传是**通用的**（任何共享账号托管都需要）；
- digest 排除项是**PlanCache 架构特有**的，离开他们的缓存机制没有意义；
- 我们如果要移植多波次，需要在自己的 visit 解析里补 `left.owner`（我们现在 `social.mjs` 没有 `ownerLeft` 相关代码，见 grep 无结果），否则只能用固定波数上限。

## 7. 分类总表与是否移植

| 多波次 raid 时间线 | **机制对方架构特有**（统一 EV 求解器 + raidSchedule）；**子模式通用**（波次列表、间隔、累计占位、胜利推进、截断保护） | **适用，P1 移植简化版**：每岛 2–3 波、按 `left.owner` 封顶、≥物理准备间隔、成功后推进不清空、执行前重新 visit 校验 |

## 9. 不建议照搬的部分与风险

- **不要整体移植统一 EV 求解器 / raidSchedule / prep-buff-loadout-stamina 建模**：依赖他们的规则版本、市场模型、装备系统和多目标优化，移植成本远高于收益。
- **不要照抄 15 秒波间隔和 3 波上限**：15 秒是他们的物理准备/节奏选择；我们的 POST minGap 2.15 秒、访问耗时和换装逻辑不同，应按 `physicalPrepLeadSec` 计算。3 波上限也要结合我们的 `ownerLeft` 和扫描频率。
- **不要照抄 180 秒 TTL 作为唯一手动局判断**：必须区分“我们自己的 arcade 会话”，否则会把自己锁死。
- **不要以为 journal 有 fsync**：他们的 `appendEvent` 没有 fsync；如果我们要做真正的崩溃恢复，需要自己决定是否 `fsync` 或至少做半行修复。
- **注意规则版本**：`state.arc.cur`、`left.owner`、`cnt['st'+id]` 这些字段要在我们当前 `cache/rules-*.mjs` 里确认存在再依赖；我们本地 `cache/arcade-05a5c445.mjs:132–152` 已确认 `arc.cur` 语义，但 visit 的 `left.owner` 还需要在线上回执里核实。

**总体建议**：先做 P0 的游乐馆让出和 GUI bootId，立刻消除“毁掉玩家手动局”和“GUI 连到旧进程”的风险；再做 P1 的最小事务日志和多波次，解决重启状态丢失和分批成熟漏偷；口粮 DP、tail index、PlanCache 隔离留到出现明确需求再上。
